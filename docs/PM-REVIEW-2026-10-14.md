## 0. 一句话结论 + 总体判定

**结论：不建议按当前状态对外发布。判定为「有条件发布（Conditional Go）」——必须先修 5 条 P0，其中 3 条是功能/稳定性硬伤、2 条是安全与门面问题。**

- **功能完成度是真的高**：SPEC §1~§10 共 10 大节 + §10 的 10 条补充裁定，逐条核对下来**只有 1 条（§10.6 的"无事件→RiskLevel=none"）未落地**，README 的核心承诺（老化灰度、聚合下钻、NAT 修复、JA4、事件去重、误报自动加白）**代码里都存在且可用，没有夸大**。
- **但存在一个会在生产环境必崩的并发缺陷**（P0-1：`Detector.Evaluate` 的基线 map 无锁，HTTP 上传同步评估与 30s 周期评估并发时触发 Go runtime `fatal error: concurrent map writes`，进程直接退出，且 `gin.Recovery()` 拦不住 fatal error）。
- **以及一个产品级记忆缺陷**（P0-2：拓扑节点/边**完全不落库**，`store` 的 `CreateNode/UpdateNode/CreateEdge` 只在单测里被调用过；进程重启＝拓扑失忆，而事件表和白名单表是持久的 → 白名单 `node:<id>` 跨重启指向错位节点，造成**静默误抑制**）。
- **安全上最危险的一条不是"没有登录"**（那是刻意的合规红线），而是 **`PUT /api/config` 与 `POST /api/events/{id}/review` 完全裸奔**：任何能访问 8080 端口的人可以把全部高危事件一键标为"误报"并自动加白、删除白名单、把 `probe_token` 置空、甚至**远程打开主动探测开关**（把合规红线从"默认关闭"变成"被他人打开"）。
- 另外 `settings.html` 有一个必然触发的 bug：**每次保存配置都会把 `probe_token` 静默清空**（P0-3）。

**发布前必须修的 5 条**：P0-1、P0-2、P0-3、P0-4、P0-5。修完这 5 条（合计约 2~3 人日）即可发布 V1.0，其余 P1/P2 进 V1.1 backlog。

## 5. P0 问题（阻断发布）

### [P0-1] `Detector.Evaluate` 基线 map 无锁并发写 → 进程 fatal crash
- **位置**：`internal/detect/reverseproxy.go:73-80`（`egressTracker.baseline` 裸 map）、`:116/124/144`（三处写）、`detect/detector.go:82`（`Evaluate` 无互斥）、`api/server.go:918`（`evaluateAsync` HTTP 内同步调用）与 `detector.go:71`（30s 周期 goroutine）
- **现象**：两个 goroutine 同时进入 `evalUnknownEgress` → `fatal error: concurrent map writes`。`fatal error` 不走 `panic()`，`gin.Recovery()` **拦不住**。
- **影响**：不可恢复崩溃。运维在页面上先后 30s 内上传两个 PCAP、或上传撞上周期评估即触发。对一个"7×24 常驻"引擎＝**服务随机自杀**。同理 `d.started`（`detector.go:85`）、`d.Cfg`（`detector.go:58`）无锁共享写。
- **建议**：① `Detector` 加 `sync.Mutex`，`Evaluate()` 入口加锁，覆盖 baseline/started/Cfg；② 更彻底：`evaluateAsync` 改为向 detector 投递"请评估"信号（channel），由 `Run` 单一 goroutine 串行执行；③ CI 加 `go test -race ./...` + 并发用例。
- **工作量**：M（半天含回归）

### [P0-2] 拓扑节点/边完全不持久化 → 重启失忆；白名单 `node:<id>` 跨重启错配静默误抑制
- **位置**：`store/sqlite.go:152/163/223/234`（node/edge CRUD **仅单测调用**）；`main.go:70-75`（每次启动空引擎）
- **现象**：`store` 的 node/edge CRUD 生产代码从未调用；`SaveSession` 只写不读（sessions 表死数据）。
- **影响**：① 重启＝拓扑全丢，`systemctl restart` 后首页空白；② **更隐蔽**：events/whitelist 表持久，但 `node_id` 内存自增重启从 1 重来 → 历史事件 NodeID 指向全新节点；误报自动加白写入的 `node:<id>`（`review.go:69`）重启后命中**完全无关节点**，**静默加白、永久抑制告警**——安全产品最糟的一类 bug：不报错、不告警、只是悄悄少报。③ 事件变"孤儿"（`server.go:429-431`）。
- **建议**：
  - **A（正确解，L）**：稳定 `NodeKey`（优先 MAC，无 MAC 用主 IP）作持久化主键；启动 `ListNodes()` 载入重建索引；Ingest upsert 批量落盘；白名单 node 维度改 NodeKey。
  - **B（止血解，M，V1.0 可发）**：不做内存态持久化，则 `review.go:68-70` 只写 `Kind=ip`；UI 移除 node 维度；README 与 settings 页写明"拓扑为内存态"。
- **工作量**：A=L，B=M

### [P0-3] 保存配置必然静默清空 `probe_token`；未授权 `PUT /api/config` 可远程打开主动探测
- **位置**：`web/settings.html:39/116-128`；`server.go:1035-1058`（GET 不回显 probe_token）、`:1166-1168`（PUT 无条件接受空串）、`:1129-1131`（probe_enabled 可写）
- **现象**：GET 出于安全不回显 token（只给 `probe_token_set`），但前端 `save()` 用**空输入框的值**覆盖该键 → PUT `{"probe_token":""}` → 鉴权被静默关闭。
- **影响**：① 运维设了 token 后，改任意配置保存即丢，无提示；② **更严重**：`PUT /api/config` 无鉴权，任何能连 8080 的人可 `{"probe_enabled":true}` **远程打开主动探测**——把"默认关闭"的合规红线变成"可被第三方开启"，在客户内网是合规事故。还可 `{"reverse_proxy_hosts":999999}` 废掉反代检测。
- **建议**：① 前端：`probe_token` 输入框为空且 `probe_token_set=true` 时不放进 PUT body，placeholder 显示"已设置（留空保持不变）"；② 后端：`probe_enabled`/`capture_enabled`/`probe_token` 加运行时覆盖开关（默认拒绝）或 false→true 变更强制审计+WARN；③ putConfig 忽略空串 token。
- **工作量**：M

### [P0-4] 无鉴权状态变更 API 暴露面：检测闭环可被"一键失效"
- **位置**：`server.go:77-103`（全部路由）、`:68-70`（仅 Recovery+CORS+空 auth）、`:117`（CORS `*`）
- **现象**：不做登录是合规红线，不算缺陷；但裸奔后果要写清：

  | 端点 | 后果 |
  |---|---|
  | `POST /api/events/{id}/review` false_positive | 任意高危事件标误报 + 自动加白节点+全部 IP，攻击者**永久隐身** |
  | `DELETE /api/whitelist/{id}` | 删白名单让压制告警重现（告警疲劳） |
  | `POST /api/whitelist` | 自建白名单＝告警开关 |
  | `DELETE /api/domains/{id}` | multi_net 规则失效 |
  | `PUT /api/config` | 见 P0-3 |
  | `POST /api/ingest/probe` | 伪造拓扑、事件洪泛（64MB body） |
  | `POST /api/ingest/pcap` | 200MB DoS（P1-1） |
- **影响**：最致命的不是被打下来，而是**检测结论被静默污染**——运营看到"无事件"，实际是被标了误报。摧毁产品可信度。
- **建议**（不违反红线）：① **默认监听改 `127.0.0.1:8080`**（`configs/config.yaml:14`、`deploy.sh:58`），对外走反代+Basic Auth/mTLS/IP 白名单，README 风险提示升为"必须"并给 nginx 片段；② CORS 收紧为白名单（新增 `cors_origins`，默认空＝仅同源）；③ 写接口加可选 `admin_token`（单令牌，不是 RBAC）；④ `AuditLog.Actor` 从硬编码 `"api"` 改为 `c.ClientIP()`。
- **工作量**：M（含 admin_token 则 L）

## 6. P1 问题（影响可用性/可信度）

### [P1-1] PCAP 上传全量读入内存 + 无并发/超时限制（M）
`ingest/pcapfile.go:85` `io.ReadAll` 200MB 进堆 + 再落盘；handler 全程同步无超时；`http.Server` 无任何 Timeout（`main.go:168`）；`ingestInFlight` 只加不读未限流；`syncTopology` 对全部历史会话 O(N²) 重放。
→ 改流式 `io.Copy` 落盘；`ingestInFlight` 真限流（超 2 返回 429）；Server 设 Read/Write/IdleTimeout；syncTopology 只处理新增五元组。

### [P1-2] 会话与节点状态无上限增长（长期运行内存泄漏）（M）
`parser.go:372-399` Finalize 不淘汰；`engine.go:67` sessions map 只增；`server.go:60/901-903` savedSessions 只增；sessions 表无索引无保留策略且 `ListSessions` 从未被调用。
→ Aggregator/Engine 加 TTL 淘汰；sessions 表加索引+保留策略；修好 P0-2 后把 sessions 当恢复数据源（变废为宝）。

### [P1-3] ARP 扫描传 `/24` 目标 100% 失败（S，30 分钟，收益极高）
`probe/scan.go:209-216`：`/24` 展开 256 地址（含网络号/广播号），在第 256 次触发 `256 > 255` 报错；去重逻辑在检查之后永远执行不到。前端占位提示正是 `192.168.1.0/24`（`ingest.html:57`），且后端因 `res != nil` 返回 200，**用户以为成功实际什么都没扫**。
→ 判断移到循环前（先算掩码位）；补 `/24` 正向单测。

### [P1-4] `/api/capture/stop` 不真正停止抓包（M）
`server.go:959-973` `ctx` 被丢弃（`_ = ctx`），消费 goroutine 从不看 ctx；pcap handle 继续跑，status 却显示 Stopped。**状态欺骗**——客户以为停了，实际还在收流量。重复 start 会泄漏 goroutine + 重复计数。
→ `StartCapture` 增加 stop channel / closeFn。

### [P1-5] 事件→节点 RiskLevel 只有单向染色永不回退（SPEC §10.6 未落地）（S）
`detector.go:138` 无条件 SetNodeRisk；`review.go` 仅 false_positive 回退。confirm/defer 后节点**永久红色**，运营会困惑"归档了怎么还红着"，久之不看颜色。
→ Evaluate 每轮把"无 pending/confirmed 事件"的节点重置 none；或 confirm/defer 分支回退。顺带处理死等级 `RiskLow`。

### [P1-6] 前端存储型 XSS：`JSON.stringify` 拼进 onclick（S）
`web/whitelist.html:79`、`domains.html:72`：`JSON.stringify` 不转义 `</script>`，innerHTML 写入导致脚本块提前终止。结合 P0-4 无鉴权 POST /api/whitelist，构成 **unauth write + stored XSS** 完整链路。
→ 改 `data-id` + 事件委托绑定。

### [P1-7] CORS 全开 `*`（S）
`server.go:115-126`：跨域可读可写，任意恶意网页的 JS 可直接操作内网 StarMap（CSRF/跨域写）。
→ `cors_origins` 白名单，默认空＝仅同源。

### [P1-8] 检测评估性能：每候选 2 次全表查询 + 全量会话重放（M）
`detector.go:120/146-159`：100 候选→200 次 `SELECT`（`db.SetMaxOpenConns(1)` 下串行）；events 表无 `(type,node_id,status)` 索引。
→ Evaluate 开头一次性拉全量建内存索引；加三个索引；大批量改异步。

### [P1-9] NAT 修复边界未说明 + WAN 侧抓包反向误合并（M）
`engine.go:257-273`：同 MAC 的公网 IP 无条件归并。WAN 侧（NAT 后）镜像时所有主机 src MAC 都是网关 MAC → **整网段归并成一个节点**，静默错图。README 把它当卖点却没写边界。
→ 归并前排除 gatewayMAC 集合；README/SPEC 写明"仅 NAT 之前（内网侧）镜像有效"；把 gatewayMAC 真正用于链路修复。

### [P1-10] JA4 c 段实现与规范/自身注释不符（M）
`parser/ja4.go:83-86`：注释说"不含 SNI 0x0000 与 ALPN 0x0010"，代码只剔 GREASE。产出指纹无法与社区 JA4 库比对（FRP 检测只匹配 a 段所以不受影响）。测试只有非空断言。
→ 过滤 0000/0010；补 FoxIO 公开向量单测；README 注明变体。

### [P1-11] deploy.sh 的 systemd Unit 组合导致起不来/抓包不可用（M）
`deploy.sh:12`（User=SUDO_USER）+ `:52`（/opt/starmap root 属主）→ 普通用户进程**无权写数据库**，反复重启；无 `AmbientCapabilities=CAP_NET_RAW`，非 root 打不开网卡 → **实时抓包默认部署必然不可用**；`:38` Go 安装包**不校验 SHA256**（供应链风险）。
→ 专用系统账号 + chown；抓包加 Capabilities；加 ProtectSystem/ProtectHome/PrivateTmp；默认监听 127.0.0.1；SHA256 校验。

### [P1-12] 审计日志前端只见最近 500 条且过滤只在这 500 条内（M）
`server.go:1198-1203`（limit 可被 `?limit=` 无上限覆盖 → DoS）；`logs.html:39/48-51`。
→ 服务端分页+过滤，limit 钳 5000；前端加"加载更多"+时间筛选。
