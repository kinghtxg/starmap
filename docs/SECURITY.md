# StarMap 安全模型

> 适用版本：1.2.0 · 更新于 2026-10-27
> 配套：[架构与实现](ARCHITECTURE.md) · [部署运维](OPERATIONS.md)

本文回答三个问题：**信任边界在哪**、**做了哪些防护**、**哪些风险要由部署方承担**。

---

## 1. 威胁模型

### 1.1 假设

| 假设 | 说明 |
|---|---|
| 部署环境 | 内网 / 隔离网，不直接暴露公网 |
| 使用者 | 受信任的安全运营人员（这是内部工具，不是多租户 SaaS） |
| 流量内容 | 可能包含攻击者构造的恶意载荷（被动分析的前提就是"网里可能有坏人"） |
| 探针 | 探针部署在各网段，可能被物理接触；上报链路可能是明文 HTTP |

### 1.2 主要攻击面

| 攻击面 | 攻击者能力 | 我们的对策 | 残余风险 |
|---|---|---|---|
| HTTP API | 能访问服务的任意人（未认证时） | 三级角色、输入校验、体积/条数上限、限流 | 未启用认证时等于 admin，见 §2 |
| 被动流量内容 | 构造恶意 SNI / HTTP 头 / XFF | 解析层全部有长度上限；所有输出转义 | 解析器 bug（已有 fuzz 覆盖） |
| 探针上报 | 伪造 `probe_id` / 注入任意 IP/MAC | `probe_token`（可选）、必填校验、体积上限 | 未配 token 时任何人可写入假数据 |
| 台账 CSV | 上传带 payload 的 CSV | 逐行解析失败不中断；输出转义 | — |
| 数据库文件 | 拿到磁盘 | 无内置加密（SQLite 明文） | 依赖磁盘加密 |
| 前端 | 存储型 XSS | 全站 `esc/escAttr` + CSP | 新增页面时漏转义（有动态测试兜底） |

### 1.3 明确不在威胁模型内

- 有 root 权限的本机攻击者（可改二进制、读 DB）
- 供应链攻击（依赖通过 `go.sum` 锁定，CI 跑 `govulncheck`）
- 侧信道（时序、缓存）
- 物理安全

## 2. 认证与会话

### 2.1 默认无认证：这是设计选择，不是遗漏

`auth.mode = none` 时所有请求身份为 admin。理由：

- 内网工具的典型部署是"只有运维能访问这台机器"；
- 强制配置账号会让"down 下来跑不起来"，实际结果是被人为绕过（比如放个 nginx basic auth 了事）。

**前提条件（部署方必须自证）**：

1. 服务只监听回环，或只对受信网段开放；
2. 或前面已有统一身份网关（堡垒机 / VPN / SSO 代理）。

不满足其中任一条就**必须**开 `auth.mode: local` 或 `oidc`。

### 2.2 本地账号

- 密码用 bcrypt（`DefaultCost`）存储；支持明文但会打日志告警。
- 会话 Cookie：`HttpOnly` + `SameSite=Lax` + `Secure`（`cookie_secure: true` 时）。
- 会话签名密钥 `session_secret`：不配则每次启动随机生成，**重启即全员掉线**（这是刻意的：随机密钥比硬编码默认密钥安全）。
- 登录有 **CSRF 防护**（同源校验 `sameOrigin`）。

### 2.3 登录失败限流

| 维度 | 阈值 | 锁定时长 |
|---|---|---|
| IP + 用户名 | 5 次 / 10 分钟 | 5 分钟 |
| IP（跨用户名喷洒） | 20 次 / 10 分钟 | 15 分钟 |

- 超限返回 `429` + `Retry-After`。
- **回环地址跳过 IP 维度**：反代未配 `trusted_proxies` 时所有来源都是 127.0.0.1，
  做 IP 维度会把全部用户一起锁死。
- 成功登录清空用户维度计数；IP 维度只**减半**（防止"蒙对一次就归零"）。

为什么必须有：bcrypt 是故意设计成慢的，不限流时攻击者每发一个请求就让服务端烧一次 CPU，
这既是口令爆破入口，也是单请求就能触发的 CPU 放大攻击。

### 2.4 OIDC

`authorization_code` + PKCE + `state` 校验；身份服务不可达时返回 503，
**绝不静默放行**（这是 SSO 集成最常见的致命错误）。

## 3. 授权

三级角色写死在路由分组上（`internal/api/server.go` 的 `ro`/`rw`/`adm`）：

| 角色 | 边界 |
|---|---|
| viewer | 只能读。适合巡检、审计、只读大屏 |
| operator | 日常运维动作：复核、导入、探测、启停抓包、归档、扫描 |
| admin | 改配置 + 删数据（删配置等于改信任边界，删数据不可恢复） |

**判定在后端**：前端按 `data-role` 隐藏按钮只是体验优化。
直接 `curl` 打接口一样会被 403（有测试覆盖：viewer 直连 `PUT /api/config` 必须 403）。

## 4. 输入与输出

### 4.1 注入

| 类型 | 状态 | 做法 |
|---|---|---|
| SQL 注入 | 已防护 | 全部 SQL 参数化；唯一的字符串拼接是 `LIMIT %d` 且入参已被 `strconv.Atoi` + 夹取 |
| 命令注入 | 已防护 | nmap 调用用 `exec.Command(name, args...)`，不经过 shell |
| 路径穿越 | 已防护 | 静态资源拒绝 `..`；`embed.FS` 本身不允许多级跳转 |
| XSS | 已防护 | 前端全站 `esc/escAttr`；无内联 `onclick`；CSP 兜底 |
| 样式注入 | 已防护 | 域名颜色必须 `#RRGGBB` |

### 4.2 资源耗尽的护栏

| 入口 | 上限 |
|---|---|
| 任意请求体 | 2MB（PCAP 200MB / 探针 64MB / 台账 16MB） |
| 列表单页 | 2000 条（显式 `limit` 硬上限 5000） |
| 列表搜索关键字 | 64 字符（按 rune 截断；`LIKE '%…%'` 走不了索引） |
| 审计 `limit` | 夹取到 5000 |
| 会话表 | 20 万条，超出丢弃并计数 |
| 扫描任务表 | 50 个 |
| XFF 解析 | 8 跳 / 32KB |
| 单主机指纹 | 32 个端口 |
| 发现主机数 | 8192 / 轮 |

**为什么列表要有上限**：`/24` 全端口扫描一次就能产出上万条端口记录，
无上限时 `GET /api/ports` 会把整表读进内存序列化成几十 MB JSON，
再交给浏览器一次性渲染——服务端 OOM、前端卡死。

**1.3.1 起是单页上限，不再是"只能看到最近 N 条"**：列表支持 `limit`/`offset` 真分页，
配合服务端 `q` 搜索可以取到任意深度的数据。此前超过上限的部分前端够不到，
会让用户得出"这台机器不存在"的错误结论（详见 [RELEASE-1.3.1](RELEASE-1.3.1.md)）。

**搜索关键字的两个安全细节**：

- `%` `_` `\` 全部转义并显式 `ESCAPE '\'`。不转义时搜 `%` 命中全表，
  虽然不构成注入（参数仍是绑定的），但会让"搜索"这个功能在语义上失效。
- 关键字长度截断到 64 字符：`LIKE` 无索引可走，超长模式串是零成本 CPU 放大点。

### 4.3 字段级校验

- 长度按**字符数**（中文按字节算会被误判）
- 网段必须 `net.ParseCIDR` 通过
- 颜色必须 `#RRGGBB`（进 SVG/CSS）
- 白名单 `kind` 白名单枚举

### 4.4 错误信息

500 一律返回"服务内部错误"，详细原因（含 SQL/路径）只进日志。
`request_id` 让运维能把用户报错和日志对上。

## 5. 传输与浏览器侧

| 措施 | 值 | 挡什么 |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | MIME 嗅探导致的脚本执行 |
| `X-Frame-Options` | `DENY` | 点击劫持 |
| `Content-Security-Policy` | `frame-ancestors 'none'` 等 | iframe 套用、外部脚本、`eval`、表单外发 |
| `Referrer-Policy` | `same-origin` | 内网地址泄漏 |
| `Permissions-Policy` | 关闭地理位置/麦克风/摄像头 | — |
| CORS | 默认不发 `Access-Control-Allow-Origin` | 任意网页跨域读写内网 StarMap |

**CSP 的 `'unsafe-inline'` 是已知妥协**：产品零构建、页面全内联脚本。
即便如此，CSP 仍挡住外部脚本注入与 `eval`，属于"有比没有强一个量级"。

**Cookie 属性**：`HttpOnly`（JS 读不到）、`SameSite=Lax`（跨站 POST 不带 Cookie）、
`Secure`（走 HTTPS 时必开）。

## 6. 审计

所有写操作落 `audit` 表：

| 字段 | 说明 |
|---|---|
| `actor` | 登录身份；未启用认证时为来源 IP |
| `action` | 动作码（`event_confirm` / `config_update` / `discover_start` …） |
| `target` | 操作对象（事件 ID / 节点 key / 网段） |
| `detail` | 附加说明 |
| `created_at` | UTC 时间 |

保留期 `audit_retention_days`（默认 90 天）由后台维护循环执行——
**这条链路在 1.2 之前是断的**（清理函数写了但没人调用，配置项等于装饰）。

审计**不可通过 API 修改或删除**，只有保留期清理会移除过期记录。

## 7. 敏感数据

| 数据 | 位置 | 说明 |
|---|---|---|
| 探针令牌 | `probe_token`（config + DB） | `GET /api/config` 只回显"是否已设置"，不回显明文 |
| 指标令牌 | `metrics_token` | 同上 |
| 账号密码 | `auth.users[].password_bcrypt` | bcrypt；配置文件权限应设 600 |
| 会话密钥 | `auth.session_secret` | 未配置时随机生成，不入库 |
| 资产底账 | `assets` / `ledger` 表 | **这是本产品的核心敏感数据**：谁有什么设备、归属谁 |

> `/api/config` 对 `probe_token` / `metrics_token` 的处理原则：
> 前端提交留空 = 不改（避免"打开设置页一保存就把令牌清了"）。
> 这是 1.1 修的一个真实 P0。

## 8. 已知风险（部署方需知）

| 风险 | 影响 | 缓解 |
|---|---|---|
| 默认无认证 | 能访问端口的人即 admin | 只绑回环 / 开认证 / 前置身份网关 |
| 探针未配 token | 任何人可写入伪造资产 | 配 `probe_token`，探针链路走内网隔离区 |
| DB 明文 | 拿到磁盘即可读全量资产底账 | 磁盘加密（LUKS / BitLocker） |
| 内网 HTTP 明文 | 会话 Cookie 可被嗅探 | 前置 HTTPS 反代 + `cookie_secure: true` |
| CSP 含 `'unsafe-inline'` | XSS 时缺一层兜底 | 转义仍是主防线（有动态测试） |
| 无 RBAC 细分 | 只有三级角色，不能按网段授权 | 定位使然；多租户需求请拆实例 |
| 主动扫描的授权风险 | 会在目标侧留连接记录 | 默认关闭 + 独立开关 + 速率上限 |

## 9. 安全测试覆盖

问题不是"有没有写防护代码"，而是"防护是否真的生效"。当前覆盖：

| 层面 | 用例 | 位置 |
|---|---|---|
| 安全响应头 | 静态页 / API / 404 三条路径都要带全 | `internal/api/security_test.go` |
| 请求体上限 | 超限 413 + 正常配置仍可保存 | 同上 |
| 列表护栏 | limit 夹取、offset 分页、总数头 | 同上 |
| 字段校验 | 超长中文、非法 CIDR、样式注入、超量网段 | 同上 |
| 登录限流 | 定向爆破、密码喷洒、回环特例、窗口解锁、清理不误删锁定 | `internal/auth/loginlimit_test.go` |
| RBAC | 45 个端点 × 三种角色的矩阵断言 | `internal/api/rbac_test.go` |
| SQL 注入 | 参数化查询 + 模糊测试 | `internal/store/*_test.go` |
| 解析器健壮性 | XFF / ClientHello / HTTP Host 模糊测试 | `internal/parser/fuzz_test.go` |
| 依赖漏洞 | `govulncheck` 阻断（0 可达漏洞） | CI |
| 静态检查 | `staticcheck` 阻断（0 项） | CI + `make lint` |
| 公钥合法性 | JWKS 的 ES256 公钥必须落在 P-256 曲线上，不在曲线上的点直接拒绝 | `internal/auth/oidc_test.go` |
| XSS（动态） | 把 payload 写进 6 类用户可控字段，真浏览器验证不执行 | 发布前手动：`scripts/ui-smoke.py` 同类思路 |

**动态 XSS 验证的三条判据**（缺一不可）：① DOM 里不出现注入的元素；
② payload 以文本形式可见（说明是被转义而非丢弃）；③ `window.__xss` 未被设置。

## 10. 报告安全问题

请**不要**开公开 Issue。通过 GitHub Security Advisory 或邮件联系维护者，
说明：版本、复现步骤、影响面、PoC（如有）。我们承诺 72 小时内响应。

修复节奏：高危问题打 patch 版本并公开 advisory；低危问题随下个版本发布。
