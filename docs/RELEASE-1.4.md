# StarMap 1.4.0 发布说明 — 独立探针

发布日期：2026-10-27

---

## 这一版要解决什么

前面几版解决的都是"拿到包之后怎么分析"：解析、聚合、拓扑、检测、台账、并发与容量。
但有一个问题一直悬着——**包从哪来**。

在此之前只有两条路：服务端自己开网卡抓（要 `-tags pcap` + CGO + libpcap，
而且只能装在能看见流量那一台），或者人工上传 pcap 文件（事后分析）。
真实环境里这两条都不够用：**需要看的流量分散在几十上百台机器上**，
而运维机上常常没有编译器、装不了 Wireshark、也不允许为一个小工具配一整套开发环境。

所以 1.4.0 交付的是 `cmd/starmap-probe`：一个约 14MB 的单文件程序，
扔在一台能看见流量的机器上就能跑，抓包、聚合成会话、只上报元数据。

## 新增：独立探针

### 四种采集后端，全都不碰 CGO

这不是技术洁癖，是能不能落地的问题。一个需要 gcc 才能构建的探针，
在多数内网里就永远装不上。

| 后端 | 实现方式 | 依赖 |
|---|---|---|
| `afpacket` | `AF_PACKET` 原始套接字，纯 `syscall` | 无（需 CAP_NET_RAW / CAP_NET_ADMIN） |
| `npcap` | `syscall.NewLazyDLL("wpcap.dll")` 直连 Npcap | 已装 Npcap |
| `exec:` | 任何往 stdout 吐 pcap 的命令 | 该命令 |
| `file:` | `gopacket/pcapgo` 纯 Go 解析 | 无 |

`go build ./cmd/starmap-probe` 直接出单文件；linux/amd64、linux/arm64、
windows/amd64、darwin/arm64 四平台交叉编译全部通过，CI 每次都验。

Windows 那条路值得单说：不走 `gopacket/pcap`（需要 CGO），而是自己声明
`pcap_open_live` / `pcap_next_ex` / `pcap_findalldevs` 等 7 个函数签名直接调
`wpcap.dll`。刻意用**轮询式**的 `pcap_next_ex` 而不是回调式 `pcap_loop`——
后者要把 Go 函数指针交给 C，非 cgo 做不到。

### 会话聚合复用服务端同一套 Aggregator

探针没有自己写一套 TCP 会话粘合逻辑，而是直接 `parser.NewAggregator` +
`Ingest` + `Drain`，和服务端抓包/PCAP 走同一个实现。

理由很实际：两套聚合逻辑一定会分叉。分叉后的症状是"探针在跑、拓扑也有节点、
就是不报警"——没有报错、没有日志，只能靠人肉对比数字才能发现。
复用同一个实现，这类 bug 从结构上就不可能存在。

### 上报 flows 而不是 packets

一个会话一条记录，比逐包上报省一个数量级的带宽和 CPU。
关键是**不能因为聚合而丢指纹**：SNI / HTTP Host / JA3 / JA4 / XFF 全部贯通到
`probeFlow`，否则 `frp` / `clash` / `reverse_proxy` 三条规则会集体失效。

这一点有专门的验收：`scripts/e2e-probe.sh` 拿同一批 pcap，分别走"探针上报"和
"直接上传"两条路，落在两个干净实例上，**事件矩阵必须完全一致**。
只测"探针能跑"是测不出字段丢失的，必须拿直接上传当基准对拍。

### 上报失败不丢数据

有界队列（默认 20000 条）+ 指数退避（1s→30s 封顶）。服务端重启、网络抖动、
机房割接期间先攒着；超上限才丢最旧的，并把丢弃条数打进日志。

退避实现刻意不用 `time.Sleep`：这个函数跑在一秒一跳的 ticker 里，sleep 会把
下一次 tick 一起吞掉，实际重试间隔会从 2s 涨到 3s、5s……越滚越大，
表现为"服务端早就恢复了，探针还在傻等"。改成记录 `nextTry` 时间戳比对。

### 收尾顺序

```
停采集 → 等读协程退出 → 冲会话增量 → 冲上报队列
```

反过来（先 flush 再停采集）会丢数据：flush 和 `src.Close()` 之间读协程还在往
聚合器里灌，这批会话既不在这次 flush 里，也赶不上后面的队列冲刷。
`systemctl stop` 之后少一段时间的数据，而且没有任何痕迹。

## 新增：可排障

探针最常见的失败不是抓不到包，而是"抓到了、发不出去"，或者"跑起来了、就是没数据"。
这两种都不报错，所以给足抓手：

- `-report 5s` 每 5 秒打一行 `frames / packets / sessions_sent / active`，
  **链路卡在哪一段一眼可见**：frames=0 是没抓到，packets=0 是链路类型不对，
  sessions_sent=0 是没聚出会话，sessions_sent 涨但页面没数据是上报失败。
- `-dry-run` 不上报只统计。
- 启动时探一次 `/api/health`，连不上直接给一行明确的 WARN，而不是让人去查抓包。
- `-list-ifs` 在 Windows 下按 **IP** 列网卡。这一条是被真实环境逼出来的：
  本机真正连业务网的那块网卡 `Description` 是**空字符串**，靠描述文字选网卡
  必然选错，而选错的症状正好是"探针能起、日志正常、frames=0"。
- 服务端返回的错误体现在会按 rune 截断再打进日志（原先按字节硬切，
  中文错误信息切出半个汉字，反而看不出原因）。
- exec 后端的 stderr 若是 GBK（中文 Windows 的 cmd.exe 就是），会先转码再打；
  采集命令的 15 秒内必须吐出 pcap 头，否则报错退出而不是永久卡住。

## 修复：`multi_net` 把 IPv6 链路本地地址当成网段（真实流量回归）

接上真实局域网后第一个冒出来的 `high` 级事件就是这个：

```
多网融合：同一设备接入多个网段/网络域
跨网段（/24）：192.168.31.0/24, fe80::/64
```

`topology.IsPrivate` 把 `fe80::/10` 也算作私网（对"是否内网"这个判断没错），
`Subnet24` 又把 IPv6 按 `/64` 聚合，于是**任何一台普通双栈主机**
（有 192.168.x.x 也有 fe80::xxx）都被判成"一机两网"。

链路本地地址是每块网卡各自一段的本地地址，和"接入了几张网"毫无关系。
已在网段维度排除 IPv4 `169.254/16` 与 IPv6 `fe80::/10`。

误报比漏报更伤：值班的人被这种事件刷几天，后面真事件就不看了。
这条修复附了负向验证——去掉过滤后测试立即变红，evidence 里能看到
`fe80::/64` 和 `169.254.10.0/24`。

## 部署形态

- **配置文件**：`-config probe.yaml`。优先级 `内置默认 < 配置文件 < 命令行显式参数`
  （用 `flag.Visit` 实现，所以配置里的值不会被 flag 默认值悄悄盖掉）。
  十几个 flag 拼进 systemd 单元或 Windows 服务的 `binPath`，既没法审阅也没法 diff，
  改一个值就要重建服务——这在企业内网是两种量级的操作。
- **systemd**：用 `setcap cap_net_raw,cap_net_admin=eip` 后以非 root 常驻，
  `AmbientCapabilities` 声明最小权限。
- **Windows**：Npcap + 管理员/SYSTEM 运行；任务计划程序或 NSSM 均可。
- 完整手册见 [PROBE.md](PROBE.md)（含排障表、资源实测、安全边界）。

## 已知边界（别指望这几件事）

1. **不解密 TLS**。看到的是 SNI / 证书 / JA3 / JA4 和流量特征，不是正文。
2. **看不见不流经它的流量**。接在接入交换机普通口上只能看见本机流量；
   要看全局必须接镜像口/分光器，或者装在被监控的那台机器上。
   这是物理拓扑问题，不是配置问题。
3. **混杂模式需要额权**。Linux 下 `PACKET_MR_PROMISC` 要 `CAP_NET_ADMIN`，
   少了这一步接镜像口会"起来了但没数据"（日志里会有明确 WARN）。
4. **Windows 不是原生服务**。探针不实现服务控制协议，需要计划任务或 NSSM 包装。
5. **不支持热加载配置**。改配置要重启进程（重启会先把队列冲干净，不丢数据）。
6. **没有做端到端加密**。探针到服务端是 HTTP，token 明文。跨不可信网段请走
   反向代理加 TLS，或用内网隔离。

## 升级说明

- 服务端无破坏性变更，1.3.1 的配置与数据库可直接升级。
- `multi_net` 的判定口径变了（不再把链路本地地址计入网段），
  升级后**历史上由 fe80 触发的 `multi_net` 事件不会自动关闭**，
  建议在事件页把它们标为误报。
- 新增 CI 产物 `starmap-probe-<os>-<arch>`，随 release 一起发布。
