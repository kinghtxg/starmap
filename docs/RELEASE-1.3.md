# StarMap 星图 1.3.0 — 发布说明

> 发布日期：2026-10-27 · 上一个版本：1.2.0（主动发现）
> 主题：**一次完整的产品审查 —— 把"能跑"抬到"经得起看"，并把实现写清楚。**

---

## 一、这一版为什么存在

1.2 交付了主动发现，功能面是闭环的。但准备开源时有个绕不过去的问题：
**别人凭什么相信这东西能上线？**

所以这一版做的是"审查 + 加固 + 交底"：

1. 以产品经理视角把功能逐项过一遍（每个页面截图 + 真数据），
   找出"看着能用、实际会误导人"的地方；
2. 以安全审计视角把攻击面过一遍（认证、注入、资源耗尽、XSS、点击劫持）；
3. 把"为什么这么实现"写成文档——这个项目最值钱的部分不是功能，
   而是每个反直觉写法背后踩过的坑。

**结果：修掉 15 个问题（4 个安全类、3 个可用性误导、5 个容量/性能、3 个正确性），
新增 3 份共约 1600 行文档，测试从 73.3% 覆盖继续加深到关键路径全覆盖。**

---

## 二、安全加固（这一版的重点）

| 问题 | 影响 | 修法 |
|---|---|---|
| **没有任何安全响应头** | 点击劫持（钓鱼页 iframe 套住控制台诱导删数据）、MIME 嗅探 | 下发 CSP / `X-Frame-Options: DENY` / `nosniff` / `Referrer-Policy` / `Permissions-Policy` |
| **请求体只有三处限长** | `PUT /api/config` 用 `io.ReadAll` 读全量 body，超大请求直接 OOM | 中间件层统一兜底：默认 2MB，PCAP/探针/台账按路径放宽 |
| **登录无失败限流** | 本地账号弱口令可爆破；bcrypt 慢哈希成了 CPU 放大器 | 双层限流（IP+用户名 5 次/5 分钟；IP 20 次/15 分钟），成功登录清零，回环地址跳过 IP 维度 |
| **500 错误把 `err.Error()` 直接回前端** | 泄漏 SQL 语句、表名、文件路径 | 统一 `internalError()`：详细原因进日志（带 request_id），客户端只拿人话 |
| **写接口无字段级校验** | 1MB 的"归属单位"能落库，之后每次列表/审计翻页都变慢 | 长度按字符数限制（名称 128 / 备注 2000 / 描述 512），CIDR 必须合法，颜色必须 `#RRGGBB` |

CSP 说明：产品零构建、页面全内联脚本，所以保留 `'unsafe-inline'`。
即便如此，CSP 仍挡住外部脚本注入、`eval`、表单外发与 iframe 套用。

## 三、容量与稳定性

| 问题 | 后果 | 修法 |
|---|---|---|
| **列表接口无上限**（端口/事件/资产/审计） | 一次 /24 全端口扫描产出上万条端口记录，`GET /api/ports` 把整表塞进内存序列化，前端一次性渲染——服务端 OOM、浏览器卡死 | 服务端护栏：默认 2000 条、硬上限 5000，响应头带 `X-Total-Count` / `X-Result-Limit`，前端明确提示"仅载入最近 N 条（共 M 条）" |
| **审计保留期是空开关** | `DeleteAuditLogsBefore` 写好了却**没有任何调用点**，`audit_retention_days` 改了不生效 | 接进 `maintenanceLoop`（启动先跑一次 + 每 6 小时） |
| **事件表没有任何清理策略** | 检测引擎每 2s 评估，事件只增不减，DB 无限膨胀 | 新增 `event_retention_days`（默认 180 天），**只清已处置的**——保留期到了但没人复核的告警不能静默消失 |
| **`syncAssets` 每次读接口都全量同步** | 每台主机 1 次 SELECT + 1 次 UPSERT；1 万台 = 2 万次 SQL 往返，而 store 是单连接，期间所有请求排队 | 加 5 秒节流 + 防重入，并发请求读上一轮快照 |
| **`assetStats` 对每条资产构造一个 map** | 1 万条资产 = 1 万个 `gin.H`，纯浪费 | 直接遍历结构体算计数 |
| 事件表缺索引 | 按状态/类型筛选是全表扫 + 排序 | 补 `idx_events_status` / `idx_events_type` |

**关于分页的诚实说明**：这一版给的是**护栏式分页**（服务端截断 + 总数头 + 明确提示），
不是真分页。真分页（前端传 page/size、后端只返回当前页）列为下一版待办，
理由是它要改 4 个页面的渲染与筛选逻辑，风险高于收益，不该和"安全加固"混在一个版本里。

## 四、可用性：三个"看着正常、其实在误导人"的地方

这三处是逐页截图审查时发现的，共同点是**功能没坏，但用户会得出错误结论**。

### 4.1 事件列表的"关联节点"显示内部主键

截图里那一列是 `40`、`30`、`27`——节点在数据库里的自增 ID。
用户既不知道是哪台设备，也无法据此去拓扑里定位。**一个字段的取值错误等于整列信息无效。**

修法：DTO 增加 `NodeLabel`，按「网段 > 主 IP > MAC > 内部 ID」的顺序生成可读标识
（聚合节点显示"网段 10.10.1.0/24"，多 IP 设备显示"10.10.1.5 等 2 个地址"）。

### 4.2 未导入台账时把全部主机标成"台账外设备"

没有台账就没有参照系，"台账外"这个判定根本无从谈起。
但界面会渲染成一屏红色"台账外 25 台"——足以让人以为网里全是影子设备。

修法：`ledger_total == 0` 时显示导入引导（带"导入台账 CSV"按钮），卡片显示 0 并注明"导入台账后计算"。

### 4.3 移动端整页横向溢出 89px，且侧栏消失后无法导航

`@media (max-width:760px)` 里把侧栏 `display:none` 了——手机上等于没有任何导航入口；
同时顶栏的全局搜索框与用户胶囊是固定宽度，整页溢出 89px，出现左右滚动条。

修法：窄屏下侧栏改成**顶部横向滚动导航条**（纯 CSS，无 JS 状态），隐藏搜索框与用户名，
弹窗贴边。9 个页面溢出全部归零。

## 五、正确性与运维

- **新增 `trusted_proxies` 配置**：部署在 nginx / SLB 后面时必须配。
  不配的后果是审计里所有操作人都是 `127.0.0.1`、登录限流的 IP 维度把全网用户当成一个人。
  （代码对回环地址做了特例，不会全员锁死，但审计依然失真。）
- **`X-Total-Count` / `X-Result-Limit` 响应头**：让调用方能判断"是不是被截断了"。
- **`putConfig` 超限返回 413** 而不是笼统的 400：否则运维会去查网络，方向全错。
- **列表分页排序键补 `id`**：同一 `ip:port` 因 `node_key` 不同存在多行时，
  只按 `(ip,port)` 排序会出现"某行在两页都出现 / 都不出现"。
- **资产表加分页**（每页 50 行）：万级资产一次性塞进 DOM 会卡住浏览器好几秒。

## 八、升级注意

| 项 | 说明 |
|---|---|
| 数据库 | 只新增索引（`idx_events_status` / `idx_events_type`），无表结构变更，老库直接启动 |
| 新增配置 | `trusted_proxies`（默认空 = 不解析 XFF，与旧行为一致）、`event_retention_days`（默认 180） |
| 行为变化 | 列表接口默认最多返回 2000 条（此前无上限）；响应体不变，另有响应头 |
| 行为变化 | 未导入台账时台账对照页显示引导，不再列出"台账外设备" |
| 兼容性 | API 路径与字段全部向后兼容（只新增 `NodeLabel` / 响应头） |

**升级后建议做三件事**：

1. 若部署在反代后 → 配 `trusted_proxies`；
2. 若端口记录已过万 → 检查 `ports` 表大小，考虑调小保留期或按网段清理；
3. 打开 `/api/config` 确认 `event_retention_days` 已生效（默认 180）。
