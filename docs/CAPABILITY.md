> 版本：1.7.3-dev · 更新于 2026-11-01

## 0. 先说结论

星图到目前为止**没有在真实政务网 / 隔离内网里连续跑过**。所有数字要么来自
**模拟真值**（我们自己造的世界，答案已知），要么来自**本机压测**（单机、
回环、合成流量）。这两类证据能证明"算法对不对、边界守不守得住"，
**证明不了"现场能不能用"**——现场有真实丢包、真实设备指纹、真实规模、
真实的人乱接线。

所以下面每个能力都标了状态，三种：

| 标记 | 含义 |
|---|---|
| ✅ **自测通过** | 有自动化断言，`make test` 里跑，红了会拦 CI |
| 🟡 **仅模拟验证** | 在 `internal/simnet` 造的世界里对得上，真实网络未验证 |
| ⬜ **未验证** | 代码有，但没有能说明它对不对的证据 |

看到 🟡 和 ⬜ 不要意外：这是当前的真实状态，写在明处比写在坑里好。

## 1. 怎么验证的：自造真值

内网产品最根本的困难是**没有 ground truth**——你不知道那台设备开了几个端口、
连了几台机器，于是只能靠肉眼觉得"看起来对"。这套东西把真值造出来：

```
internal/simnet      生成"世界"（谁是设备、谁连谁、谁在哪个网段、哪个探针看得到）
       ↓ Sessions()
                  每个探针各自看到了什么（跨三层没 MAC、NAT 改写、丢包、时钟偏移）
       ↓
   引擎            → 节点 / 边
       ↓
test/truthcheck      独立校验器（刻意不 import 引擎）
       ↓
    断言：设备不能被拆、不能被吞、边不能缺、字节不能翻倍、端口不能漏
```

三条设计约束，缺一条这套东西就会退化成"自己测自己"：

1. **真值与观测分离**。`World` 是客观事实，`Sessions()` 是每个探针看到的。
   两者之间的差异才是被测对象。
2. **确定性**。同 seed 逐字节可复现（`TestDeterministic`），否则进不了 CI。
3. **校验器独立**。`test/truthcheck` 不 import `internal/topology`，不复用任何
   引擎算法——共享假设的测试永远绿。

校验器自己还有 11 个**变异测试**：把完美图逐项弄坏（字节翻倍、拆节点、并节点、
IP 重复、删边、丢端口），确认每一项都真的会红。断言被谁写软了，对应用例立刻失败。

复现：

```bash
go test ./internal/topology/ -run TestTopologyAgainstGroundTruth -v   # 8 个场景
go test ./test/truthcheck/ -v                                          # 校验器判据自检
go test ./internal/simnet/ -v                                          # 生成器自检
```

## 2. 八个场景的实测结果

| 场景 | 想证明什么 | 实测 | 状态 |
|---|---|---|---|
| `clean` 干净网络 | 下限：20 台 / 2 网段 | 20 节点、28 边、字节比 **1.000**、端口漏识 0 | ✅ |
| `dualhomed` 一机两网 | 一机两网必须**合 1 个节点** | 13 台 → 13 节点，未拆 | ✅ |
| `multiobserver` 多观察者 | 同一会话被两个探针看到，**字节不能翻倍** | 观测 2.00 倍、图上 **1.000** | ✅ |
| `nat` SNAT 跨段 | 同一份载荷两段各一次，**2 倍是上限不是缺陷** | 字节比 **2.000**（提示不断言） | ✅ |
| `skew` 时钟快 3 分/慢 2 分 | 时钟不准不该把会话判成新连接 | 观测 2.00 倍、图上 **1.000**、时间越界 0 | ✅ |
| `partial` 30% 漏采 | 漏采不该让设备消失 | 12 台全在、字节比 0.705（漏的部分本来就没看到） | ✅ |
| `conflict` IP 冲突 | 两台机器抢一个地址，**必须拆 2 节点并打标** | 2 节点、1 条 `ip_conflict` 事件、双方都带标记 | ✅ |
| `drift` MAC 不变 IP 变 | 对照组：同 MAC 多 IP 必须**是 1 台** | 2 台 → 2 节点 | ✅ |

八个场景全绿，且这个"全绿"是有判别力的——第一轮跑出来就抓到一个真缺陷（见 §3）。

## 3. 靠这套东西抓到的真缺陷

### 3.1 IP 冲突被静默合并（已修，1.7.3）

两台 MAC 不同的设备抢同一个地址时，引擎原本把新 MAC 挂到老节点上、MAC 字段保留
第一个，于是两台机器的流量、端口、告警揉成一台，**图上看起来毫无异常**。

这是最坏的处理方式：同一 IP 换 MAC 恰恰是内网最该刺眼的信号——
静态地址配错（服务时通时不通，能查一周）、DHCP 池重叠、**ARP 欺骗**
（横向移动的第一步）。图上不刺眼，就没人查。

现在：已知 MAC 时以 MAC 为身份，冲突双方各成一个节点、都打 `ip_conflict` 标记、
风险级别 mid（mid 同时让它成为锚点，不被 /24 聚合吞掉），并产出 `ip_conflict`
风险事件，证据里带两个 MAC。

### 3.2 同一会话被两个探针上报后字节翻倍（此前已修，回归已覆盖）

`multiobserver` 场景现在实测图上字节 = 真值 1.000，说明按会话增量合并是对的。

## 5. 方法的物理上限（不是缺陷，但要说清）

这五条无论怎么优化都绕不过去，写在这里免得被当成"没做好"：

1. **跨 NAT 必然重复计数**。源端口被改写、两条会话没有共同字段，被动分析无法关联。
   图上字节会是真的 2 倍（`nat` 场景 2.000）。产品该做的是**标注**这段重复，
   而不是对外声称总量精确。
2. **跨三层拿不到源 MAC**。源 MAC 已被网关替换。所以"一机两网"的判定在跨段场景
   只能靠 IP 集合，不靠 MAC 合并。
3. **只看得到被访问过的端口**。一台机器 Listen 80/443，整段没人访问 443，
   任何被动产品都看不见 443。端口画像的完整度取决于流量覆盖度。
4. **丢包只会让数字偏小**。探针过载/镜像口带宽不够时，字节和边都少
   （`partial` 场景 0.705）。缺的部分**无法补**，只能靠加探针覆盖。
5. **时钟不同步时时间线会错位**。容错到分钟级；再大就会把同一会话判成新连接。

## 6. 明确没做的事

- **没有 RBAC**：只有 viewer/operator/admin 三级门禁，没有按网段/部门的细粒度权限。
- **没有集群**：单进程单库，多实例会各算各的。
- **没有前端自动化测试**：页面靠 `ui-smoke` / `ui-writes` 脚本粗测，没有组件级测试。
- **没有 IPv6 场景**：`IsPrivate` 认 ULA（fc00::/7），但 `/24` 聚合对 v6 无意义，
  v6 地址在聚合/下钻/冲突判定里实际走哪个分支，没有任何用例覆盖过。真值世界里
  也一个 v6 地址都没有。
- **无线/VLAN 未建模**：真值世界里没有 VLAN tag、没有 AP/STA 关系。

## 7. 下一步（按"能不能真正用"排序）

1. **真实 PCAP 回放**：拿现场脱敏流量跑一遍，对比人工台账——这是唯一能验证
   🟡 那批能力的办法。
2. **物理位置**：SNMP 读 ARP/MAC 表 + LLDP/CDP 邻居，才能回答"这台机器在哪个柜子"。
   现在只有探针位置（"A 栋 3 层"），粒度差一个数量级。
3. **证据等级**：同一个结论（"这是一台打印机"）可能来自 MAC 前缀、端口组合、
   HTTP 头，可信度差很多。现在全混在一起，用户无法判断该不该信。
4. **规模验证**：万级主机下评估耗时、内存、页面响应，目前只有千级数据。
