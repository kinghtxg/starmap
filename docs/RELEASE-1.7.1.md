# StarMap 1.7.1 发布说明

> 主题：**三笔长期在线跑才会露出来的账——而且它们都不报错。**
> 发布日期：2026-11-01 · 上一个正式版：1.7.0 · 无 schema 变更，可直接替换二进制

---

## 一、这一版在解决什么

三个问题，都没有新功能，共同点是**出错时没有任何地方报警**：

| 现象 | 看起来像 | 实际是 |
| --- | --- | --- |
| 总流量数字变大 | "网络更忙了" | 强杀重启后仍在持续的会话被整笔重算 |
| 页面越用越慢 | "数据多了" | 站点列表每次跑两遍全表聚合 |
| 磁盘莫名满了 | "日志太大" | WAL 只涨不缩，写满后 SQLite **静默失败** |

它们都不产生日志、不返回错误码，只能靠判据把它钉住。所以这一版的重点一半在代码，
一半在**用例怎么断言**（见第四节）。

---

## 二、强杀重启后，在途会话的流量被整笔重算

### 问题

会话增量基准（`session_offsets`）此前只在 60 秒的计数档里刷新一次。新会话于是有
最多 60 秒完全没有底数——而探针每 5 秒就会重发一次累计值。

强杀、掉电、OOM、任务管理器结束进程，正好落在这个窗口里。重启后第一份快照被当成
"从 0 长到这里"：

```
上报 1,000,000 字节 → 结束进程 → 重启 → 同一份快照再报一次 → 总流量再涨 1,000,000
```

崩几次就翻几倍。界面上只是一个更大的数字，拓扑、端口、风险评分照样出结论。

### 修法：基准分两档落盘

- **快档（每一拍，2s）**：只写"从没落过库"的基准，按 `offsetFlushBatch = 2000` 截断。
  2000 行 / 2 秒对 SQLite 是很轻的负载，而稳态下新会话速率远低于此
  （真实网络每秒几十到几百条），正常情况下底数两秒内一定已经落库。
  爆发式灌库（导入 pcap 可能瞬间造出十万条会话）超出的部分排到下一拍，不阻塞上报。
- **慢档（60s）**：与原来一致，把变脏的基准全量刷一遍。丢了只影响"上次落盘以来的增量"，
  量是有界的。
- 被截断的部分不会被忘掉：`freshOffsets` 记住本拍没写出去的量，下一拍继续，直到为 0。

### 兜底：认出"跨进程启动的在途会话"

快档仍有 2 秒窗口，强杀还是可能赶上。所以增加一条判断：重启后某条会话"第一次见到"、
`FirstSeen` 早于本次启动、且 `LastSeen` 仍在活跃（含 **2 分钟探针时钟偏差容差**）时，
把它当成上一个进程的遗产——**以当前快照为底数，本次不产生增量**。

判据刻意收得很窄，三个条件缺一不可：

1. **库里有上一个进程的痕迹**（恢复出的基准条数或边字节非 0）；
2. `FirstSeen` 早于本次启动；
3. `LastSeen` 不早于本次启动（容许 2 分钟偏差）。

第 3 条挡的是**历史 pcap 导入**：那种会话两端的 `FirstSeen` / `LastSeen` 都来自报文本身、
都在过去。只判 `FirstSeen` 的话，导入的整批流量会被当成"上个进程的遗产"一笔不记——
那是数据消失，比数字偏大严重得多。

第 1 条挡的是同一类错的反面：全新库（首次部署、单元测试）里什么都没有，说明之前根本没有
进程统计过这些字节。少了它，**空库上摄入的第一条会话的边字节恒为 0**，而界面上只表现为
"这台机器没流量"。两种错都难查，取数据消失更糟的那一侧时，必须先把"有没有历史"判清楚。

## 三、WAL 只涨不缩；站点列表跑两遍全表聚合

### WAL

WAL 模式的隐式 checkpoint 只在提交时发现 WAL 超过 1000 页（约 4MB）时做一次 **PASSIVE**
checkpoint，而站点视图这种"全表聚合"的重读很容易与它撞上，于是 WAL 只能一路涨。
更关键的是 **checkpoint 之后文件不会自动缩容**：一次持续灌入把它撑到 193MB，它就永远是
193MB——主库才 145MB，重启却要 replay 这 193MB。

而磁盘写满时，SQLite 的表现是**写入静默失败**：接口仍回 200，数据没进去。

- 连接串加 `journal_size_limit=64MB`；
- `Store.CheckpointWAL(truncate)`：5 分钟一次 PASSIVE，退出前一次 TRUNCATE
  （退出时是唯一"没有读者挡着"的时刻）；
- 导出 `starmap_db_wal_bytes`：让"只涨不落"在变成故障之前就能看见。

### 站点列表

站点是 `ports` 上的派生视图，列表页要总数做分页，于是一次请求跑两遍
CTE + GROUP BY + 两次 LEFT JOIN。两万站点规模上单遍约 50ms，纯 Go 驱动还要再乘一倍多。

- **没被截断时不问库**：`limit` 是硬上限，取回的条数少于它就不可能被截断，本页条数就是总数。
  绝大多数中小部署站点数不到 2000，等于把一次全表聚合整个省掉。
- 真被截断时才问库，结果短时缓存 5 秒。**失效点挂在写路径上**，不只靠 TTL：
  扫描器刚写入 200 个新站点、用户刷新仍看到旧总数，这种不一致比慢更难解释。
- 带筛选条件不缓存：条件组合太多，命中率低而失效逻辑复杂，收益抵不上出错的机会。

## 四、测试：这一版的判据比代码更值得看

四条经验，都是踩过的：

1. **pragma 拼错不会报错。** SQLite 静默忽略未知 pragma，症状只有"页面莫名变慢"。
   所以 `TestPragmasEffective` 逐项读回实际值比对（`busy_timeout` / `cache_size` /
   `temp_store` / `synchronous` / `mmap_size`），而不是断言"连接串里有这个参数"。
2. **断言写的是"快不快"，要守的是"结构对不对"。** 绝对耗时会被冷缓存、行宽、跑测试的
   磁盘三件事干扰。容量用例改为断言执行计划：`assertNoFullScan` 要求变更视图的查询
   里不许出现 `SCAN ports`——"成本不随表总量增长"只有这一个判据。
3. **缓存最容易出的不是"没命中"，而是"该失效时没失效"。** 四条写路径（单条 upsert、
   批量 upsert、标记 stale、按 node_key 删除）逐一验证，另外单独验证筛选条件不走缓存。
4. **总数分支写错不会报错，只会让用户翻不到最后几条。** `TestSitesListTotal` 把
   「未截断 / 正好一页 / 被截断 / 带 offset」四条分支各给一条断言。

新增用例：

- `internal/topology/crashbridge_test.go`（5 条）：新会话底数第一拍落库、底数丢失后不重算、
  历史 pcap 导入不被误伤、冷启动新会话照常计入、快档限流与后续拍次补齐。
- `internal/store/sitecount_test.go`（3 条）+ `internal/api/sites_test.go:TestSitesListTotal`。
- `internal/store/pragma_test.go`：pragma 生效性。

## 五、升级与兼容

- **无 schema 变更**，无配置项变更，直接替换二进制即可。
- 首次启动会因 `journal_size_limit` 对新 WAL 生效；**历史遗留的大 WAL 文件**
  会在第一次 checkpoint 后缩容，不必手工删 `-wal`（手工删等于放弃未 checkpoint 的数据）。

## 六、已知短板（未变）

- 站点列表仍是"服务端取一页 + 前端本地分页"，站点总数超过 2000 时前端只能拿到前 2000 条。
  真·服务端分页在待办里。
- 快档 2000 条是**按行数**限的，不是按字节。会话字段明显增加时需要重新标定。
- WAL 体积只导出指标，没有内置阈值告警——告警通道本身还没做（见 1.7.0 第六节的对标结论）。

## 七、怎么复现这几条

```bash
# 崩溃重启不重算（含历史 pcap 不被误伤、冷启动照常计入）
go test ./internal/topology -run 'CrashBridge|Restart|Historical|FreshSession' -v

# 快档限流与后续拍次补齐
go test ./internal/topology -run TestOffsetFlushBatchIsBounded -v

# 站点总数：缓存失效 + 四条分支一致性
go test ./internal/store -run TestSiteCount -v
go test ./internal/api  -run TestSitesListTotal -v

# pragma 真的生效（拼错不会报错，只能读回来看）
go test ./internal/store -run TestPragmasEffective -v
```
