# StarMap 星图 — 超大规模内网可用性分析与升级方案（PM-SCALE-V2）

> 撰写：Product Owner（极客星空安全实验室）· 日期：2026-10-19
> 对应需求：创始人「用 PostgreSQL 处理大量涌入的数据包 / 提升并发处理能力 / 提升发现能力 / 用户能随时增加和处理未知节点 / 在超大规模内网真正发挥作用」
> 代码基线：`starmap` V1.3（README/SPEC/CHANGELOG 与 `internal/*` 逐文件实读）
> 硬约束：**单人开发 + AI 辅助 + 业余时间**
> 本文档只做产品分析与方案设计，不含实现代码。全部结论附代码行号证据；属推算的数字已显式标注「推算，需实测标定」。

## 0. 执行摘要（结论先行）

**创始人的直觉对了一半：「并发处理能力」确实不够，但瓶颈不在数据库，而在管道本身。换成 PostgreSQL 解决不了任何一个真正会先崩的环节，却会毁掉「零依赖单二进制、内网一键部署」这个最核心的竞争力。**

一句话判定：

> **当前 StarMap 撑不住超大规模内网的原因不是「写不进数据库」，而是「每 2 秒把全部历史会话重放一遍 + 会话永不淘汰 + 前端全量渲染」。这三条里没有一条是 PostgreSQL 能解决的。**

更关键的误判：在真实的大规模内网里，客户**根本不可能给你一个能看全网的镜像口**。约束首先是「看不见」（采集覆盖），其次是「看不完」（运营带宽），最后才是「写不进」（中心端吞吐）。把预算压在中心端数据库上，是在解决一个排第三的问题。

| 创始人诉求 | 我的判定 | 依据 |
|---|---|---|
| 用 PostgreSQL 处理大量涌入的数据包 | **不建议现在做（P2，设触发条件）** | 见 §1.5。单进程单写者，SQLite 的并发短板用不上；换 PG 后同样的写入模式会更慢；部署复杂度是单人项目的长期负债 |
| 提升并发处理能力 | **真实需求，但解法是「去全量重放 + 分片聚合器」，不是换库** | 见 §1.2/§1.3 |
| 提升发现能力 | **真实且高价值，但最大缺口是没有官方探针 agent 与没有台账对照** | 见 §4 |
| 用户能随时增加和处理未知节点 | **功能定义需澄清；当前实现有一个会让核心价值静默失效的严重缺陷** | 见 §3（含 P0 级 bug：聚合网段内的主机永远进不了资产库） |

**最该做的三件事**（详见 §6）：
1. 把「每 2 秒全量重放所有会话」改成增量 + 加会话淘汰（约 1 周业余时间，可用规模从 ~1 千台抬到 ~1 万台，部署形态零变化）。
2. 把「发现能力」的预算花在采集覆盖与运营闭环上：官方轻量探针 agent + 台账导入对照 + 账外资产批量处理。
3. 给所有列表和拓扑图设服务端上限与前端 LOD，否则 1 万节点时「功能存在但人用不了」，等于没做。

## 1. 现状瓶颈诊断（量化）

### 1.1 数据流与每环节成本模型

```
PCAP 文件 ─► ingest/pcapfile ─┐
网卡抓包 ─► ingest/capture  ─┼─► parser.Aggregator ─►（2s 全量 Finalize）─► topology.Engine.Ingest
远端探针 ─► ingestProbe ────┘        │                                              │
                                     │◄── Detector.Evaluate（30s，SessionsFunc=Finalize）
                                     ▼                                              ▼
                            sessions 表（只写不读）                    nodes/edges（2s 节流 flush）
                                                                                    │
                                                                     Snapshot() ◄───┘
                                                                        │
                                          /api/topology  /api/stats  syncAssets（3 SQL/节点）
                                                                        ▼
                                                                   web/assets/topo.js（全量 SVG 重建）
```

**单位成本估算**（推算值，需在 §5 P1-8 用压测标定；假设：现代 x86 服务器、SSD、Go 1.22、空闲系统）：

| 操作 | 估算单条成本 | 依据 |
|---|---|---|
| gopacket 解码 + `ParsePacket` | 3–8 µs/包 | 纯 Go 逐层解码 Ethernet+IP+TCP/UDP |
| `Aggregator.Ingest` | 1–3 µs/次 | `FiveTuple.Key()` 三次字符串拼接（`model.go:95-102`）+ map 读写 |
| `Engine.Ingest` | 1–3 µs/次 | 全局写锁 + 4 次 map 访问 + 幂等累计（`engine.go:383-493`） |
| `Snapshot()` | 约 1–3 µs/节点 + 1–2 µs/边 | 全量拷贝 + `APINodeID` 字符串构造 + 两次 `sort.Slice`（`engine.go:890-1018`） |
| SQLite 单条 UPDATE/INSERT（WAL，事务内） | 5–20 µs | `MaxOpenConns(1)`（`sqlite.go:157`），无网络往返 |
| 浏览器 SVG 节点渲染 | 约 50–200 µs/节点 | DOM 创建 + 布局 + 样式计算，经验值 |

### 1.2 五个候选瓶颈：真实 vs 臆想

| 候选瓶颈 | 判定 | 崩断点（推算） | 依据 |
|---|---|---|---|
| **① 全量重放（真正的头号瓶颈）** | ✅ **真实，且是最先崩的** | 累计会话 50 万时 2s 轮次占用 >60% CPU；100 万时轮次被打穿 | `main.go:143-157` 每 2s `Finalize()` 全量 → 逐条 `Engine.Ingest`；`server.go:987-1011` 每次接入再来一遍；`detector.go:103` 每 30s 再全量拷一次 |
| **② 内存单调增长 / 无淘汰** | ✅ **真实，7×24 必 OOM** | 50 万会话 ≈ 250MB–1GB；100 万 ≈ 0.5–2GB | `parser.go:410-437` Finalize 不淘汰；`engine.go:113` sessions 只增；`server.go:62` savedSessions 只增；`parser.go:380-382` packetGaps/packetLens **永不裁剪** |
| **③ SQLite 写并发** | ⚠️ **真实但排第三** | 1 万活跃节点 + 8 万活跃边时 flush 约占 45% 周期 | `sqlite.go:157` 单连接 + 2s 批量 upsert（`engine.go:272-319`）；**根因是脏集≈全量活跃集，不是引擎能力** |
| **④ Aggregator 单锁** | ⚠️ **真实但只在特定部署形态下成立** | 中心端单网卡抓 10G（≈1.8M pps）时必崩；探针/PCAP 形态下不成立 | `parser.go:282` 单 `sync.Mutex`；单核解码上限约 12–30 万 pps |
| **⑤ Detector 串行评估** | ❌ **不是瓶颈（别动它）** | 串行本身没问题；问题是它每轮做 O(N) 全量遍历 + 每个候选 2 次全表扫描 | `detector.go:94-96` 整轮串行化（P0-1 修复）；`detector.go:161-174` findRecent 每次 `ListEvents` 全表 |
| **⑥ 前端渲染** | ✅ **真实，确定不可用** | 节点 >2000–5000 时交互明显卡顿；>1 万时页面假死 | `topo.js:20-22` 只有 `LABEL_HIDE=240`/`FLOW_MAX_EDGES=420`，**无任何节点上限**；`topo.js:389-507` 每次 `render()` 全量重建 SVG 字符串 |

**臆想的过度设计（明确排除）**：分布式消息队列、ClickHouse/ES、微服务拆分、把 Detector 并行化、前端重写为 WebGL。理由见 §6.2。

### 1.3 崩断点推演表

设 N = 累计会话数（**注意：由于无淘汰，N 随运行时长单调增长，与设备数非线性相关**）。

| 规模 | 典型 N（跑 1 周） | 每 2s 轮次成本（推算） | 先崩环节 | 用户可感知现象 |
|---|---|---|---|---|
| **≤500 台 / 单次 PCAP ≤200MB** | ≤5 万 | ~0.13 s（6%） | — | 完全正常 |
| **1–3 千台 + 单探针常驻** | 5–20 万 | 0.13–0.5 s（6–25%） | `syncAssets` 3N 次 SQL + `Snapshot` | `/api/assets` 1–3s；内存缓慢上涨 |
| **5 千–1 万台** | 20–100 万 | 0.5–2.5 s（25–125%） | **全量重放 + 内存** | 2s 轮次打穿；RSS 1–3GB；flush 与 API 抢同一连接 → 页面偶发数秒；拓扑页卡顿 |
| **>1 万台 / 探针 ≥20** | >100 万 | >2.5 s（打穿） | 全链路 | 重放周期失效、OOM、API 超时、前端假死 |

**多探针场景是最先崩的**（这是最值得警觉的一条）：

`ingestProbe`（`server.go:741-854`）每收到一次上报就触发一次 `syncTopology()`（全量 Finalize + 全量 Ingest + 全量 extractPorts + 全量 syncAssets）+ `evaluateAsync()`（全量 Evaluate）。即：

```
单探针上报成本 = O(累计会话总数)   ← 而不是 O(本次上报的条数)
P 个探针 × 每 30s 上报 × N=10万 → 每秒约 1.7 次全量重放 × 0.25s ≈ 43% CPU 纯无效功
```

N=10 万、20 个探针时，**CPU 全部消耗在重放已经灌过的会话上**。这是纯粹的设计缺陷，不是硬件不足。

**另一个隐藏的 O(M×E) 炸弹**：`removeNodeLocked`（`engine.go:773-778`）为删除一个节点要遍历**全部边**。而 `cleanupOfflineAssets`（`main.go:227-253`）会对每个离线账外资产调用它一次 → 清理 1000 台离线资产 × 5 万条边 = **5000 万次 map 迭代，全程持有引擎写锁**，10 分钟一次的清理任务可以让 ingest 冻结数十秒到数分钟。在 DHCP 频繁变动的大网里这会周期性发作。

### 1.4 【P0 级静默失效】聚合网段内的主机永远进不了资产库

这是本次读码发现、前两份文档均未覆盖、且**直接击穿产品核心价值**（账外资产发现）的缺陷。

链路：

1. `addSubnetMemberLocked` 在 /24 内节点数 > `aggregate_threshold`（默认 **20**）时把该网段标记为已聚合（`engine.go:601`）。
2. `Snapshot()` 对属于已聚合网段的节点执行 `continue`，**成员节点不出现在快照里**（`engine.go:894-910`）。
3. `syncAssets()` 遍历的是 `Snapshot().Nodes`（`server.go:1401-1403`），因此**成员节点从未被登记为资产**。
4. 聚合节点本身是临时构造的，`NodeKey` 为空（`engine.go:917-921`），被 `if n.NodeKey == ""` 跳过（`server.go:1405`）。

后果：

> **一个 200 台的办公 /24，只有最先被发现的前 20 台会进入资产库，剩下 180 台永远不出现。** 且这 20 台是「谁先被流量看到谁入选」的任意子集，重启后还会变。

规模越大越严重：1 万台设备的网络里，绝大多数网段都会超过 20 台 → **资产库与账外资产统计只剩零头**。用户看到的「账外资产 137 台」在 1 万台的网络里是荒谬的数字，但系统不报错、不提示，属于典型的「静默少报」。

修复方向（P0-C，见 §5）：`syncAssets` 改为遍历引擎的**全量内网节点**（新增 `Engine.AllNodes()`，带 NodeKey 且非 ext），而不是 `Snapshot().Nodes`。注意：**这个修复必须与资产同步批量化一起做**，否则节点数从几百跳到 1 万，每次 `/api/assets` 要跑 3 万条 SQL，会直接把 API 拖垮（见 §5 P0-D）。

### 1.5 PostgreSQL 到底解决什么、不解决什么（诚实评估）

| 维度 | PostgreSQL | StarMap 现状是否需要 |
|---|---|---|
| 多写者并发 / 行级锁 | ✅ PG 的核心优势 | ❌ **不需要**：单进程单写者，`MaxOpenConns(1)` + WAL 已把写并发问题彻底绕开（`sqlite.go:157-161`） |
| 高并发读（MVCC、多连接） | ✅ PG 优势 | ❌ **不需要**：使用者是 1–5 个人的 Web 控制台 |
| 跨机访问 / 网络数据库 | ✅ PG 优势 | ❌ 单二进制同机部署，本来就是本地文件 |
| 大表查询优化、分区、并行查询 | ✅ PG 优势 | ⚠️ **弱需要**：当前没有复杂查询，只有主键/唯一键点查与全表扫描；加索引即可解决（见 P0-D） |
| 生态工具（Grafana/BI/外部分析） | ✅ PG 优势 | ⚠️ 有价值但非当前用户痛点 |
| **多实例汇聚（N 台采集节点写同一中心库）** | ✅ **PG 真正有价值的地方** | ⚠️ 需求存在但**尚未被任何真实用户提出** |

**PG 解决不了的（恰恰是先崩的四件事）**：

1. ❌ 每 2 秒全量重放所有会话（`main.go:143-157`）—— 换库后照样重放。
2. ❌ 会话/采样永不淘汰导致的 OOM（`parser.go:380-382`）—— 换库后照样涨。
3. ❌ `syncAssets` 每节点 3 条 SQL、多探针触发的 O(累计会话) 重放 —— 换库后每条还多了网络往返，**不改造写入模式会直接变慢**。
4. ❌ 前端全量 SVG 渲染（`topo.js:389-507`）—— 与数据库无关。

**换 PG 的代价（对单人项目是长期负债）**：

- 破坏「零依赖单二进制、内网一键部署」这个**唯一的差异化卖点**（README:29-30）。内网装数据库通常要审批、要运维配合、要定备份策略。
- 部署步骤从「下载 exe → 跑」变成 5–10 步，首装失败率显著上升，issue 区会被「连不上数据库」淹没 —— 这是单人维护者最大的时间黑洞。
- 两套 schema、两套迁移、两套方言（`ON CONFLICT` 细节、时间类型、JSON 函数、PRAGMA）、两套部署文档与两份 bug。

**结论：PG 是 P2，且必须设触发条件。** 当前阶段正确的动作是「买期权，不付全款」——把 `store` 层接口化（0.5 天），使未来加第二个实现的改动面可控，但**现在不实现第二个实现**。

## 2. 可用性分析（产品经理视角）

### 2.1 真实用户画像

| 画像 | 场景 | 核心诉求 | 对 StarMap 的真实约束 |
|---|---|---|---|
| **A. 集团/大型企业安全运营岗（最核心）** | 常态资产测绘、账实不符核查 | 「网里到底有哪些设备、台账外还有多少」 | **没有网络管理权限**，拿不到交换机 ARP 表/CMDB；只能申请一台小服务器 + 一个镜像口或几台探针。**「能装上、不被运维拒绝」是第一需求** |
| **B. 等保/攻防演练前的资产清查** | 临时部署 3–7 天，出清单走人 | 快速出可导出的资产清单 | 不要长期运维；导出 CSV/Excel 比页面好看重要得多 |
| **C. 园区/分支网管** | 几百到两三千台，一台机器跑全部 | 零运维，一条命令起 | 单二进制是刚需；任何额外依赖都会劝退 |
| **D. 小集成商（给客户交付）** | 可复制的交付件 | 稳定、可复制、可交接 | 部署步骤越多，交付成本越高 |

**关键洞察：A 类用户（唯一真正需要「超大规模」的画像）恰恰是权限最少、最难给你全网镜像的。** 他们能做到的上限通常是：在几个汇聚点/核心交换机上做镜像，或在若干台服务器上装轻量 agent。

### 2.2 「看起来能用、实际不可用」清单

| # | 环节 | 现象 | 根因 | 在多大规模触发 |
|---|---|---|---|---|
| U1 | **资产库静默缺人** | 1 万台网络只显示一两百台账外资产 | §1.4 聚合隐藏 | **>20 台/网段即触发（几乎总是）** |
| U2 | **拓扑图几万节点** | 打开即卡死 | 无节点上限、无 LOD、全量 SVG 重建（`topo.js:389-507`） | 默认阈值下主要来自**公网 /24 外部聚合节点**（可轻松上千）+ 用户下调阈值/下钻 |
| U3 | **资产/事件列表几千条** | 几 MB JSON 一次性返回，前端全量渲染表格 | `ListAssets`/`ListEvents` 无分页（`sqlite.go:1011`、`sqlite.go:741`；`server.go:1472-1485`、`499-510`） | >2000 条 |
| U4 | **账外资产几千台怎么运营** | 只能一台一台点归档 | 归档是单条 API，无批量（`server.go:1517-1542`） | >200 台即不可运营 |
| U5 | **事件刷屏** | 无聚合、无分页、无「同一节点同类只显示一条」 | `findRecent` 只做 24h 去重（`detector.go:161-174`），UI 无聚合视图 | 几千台网络的常态 |
| U6 | **重启后要重新认识网络** | 重启后拓扑靠库恢复，但学习期清零、基线清零，头 10 分钟不出 unknown_egress | `detector.go:56/111` 学习期不持久化 | 每次重启 |
| U7 | **探针离线无人知** | 探针停了，拓扑看起来还在（只是不再长） | 有 `probes` 表但无状态机、无离线判定（`sqlite.go:1155-1179`） | 只要用了探针 |
| U8 | **抓包「已停止」实际还在跑** | 状态欺骗 | `server.go:1073` `_ = ctx`（P1-4，V1.3 未修） | 任何时候 |
| U9 | **PCAP 大包上传** | 200MB 文件峰值 400MB 堆，同步阻塞无超时 | `pcapfile.go:85` `io.ReadAll`；`main.go:194` 无超时 | >100MB |
| U10 | **周期性冻结** | 每 10 分钟卡一次（数十秒） | §1.3 末尾的 O(M×E) 清理 | 大网 + DHCP 频繁变动 |

### 2.3 部署可用性：引入 PostgreSQL 的代价

现状部署路径：`下载 starmap.exe → 写 config.yaml → ./starmap` —— **1 步**。这是它在 GitHub 同类项目里最强的竞争力（多数同类要 docker-compose 起 3 个容器）。

引入 PG 后：`装 PG → 建库建账号 → 配 pg_hba → 改连接串 → 处理内网防火墙 → 备份策略 → 升级时的 schema 迁移` —— **7 步以上**，其中至少 2 步需要别的部门配合。

**取舍判断**：

- 90% 的用户场景（几百到 3 千台）SQLite **根本不构成瓶颈**（§1.3 表：N≤20 万时 DB 只占 6–25%）。
- 为 10% 的场景牺牲 90% 场景的部署体验，**是明确的错误取舍**。
- 且这 10% 场景的真瓶颈也不是 DB（§1.2）。

### 2.4 是否需要「双存储」策略？—— 我的判断：**不做**

| 方案 | 判断 | 理由 |
|---|---|---|
| A. 强制 PG | ❌ 反对 | 毁掉部署卖点，收益不成立 |
| B. **SQLite 默认 + PG 可选（双存储）** | ❌ **现阶段反对** | 双存储 = 两套 schema + 两套迁移 + 两套部署文档 + 双份 bug。单人维护下这是**永久负债**，而收益要等「多实例汇聚」需求出现才兑现。且「可选后端」会吸引用户去踩你不常测的那条路径 |
| C. **SQLite 唯一后端 + `store` 层接口化（预留 PG 位）** | ✅ **推荐** | 0.5 天买一个期权，不加任何用户可见复杂度。真到需求出现时，实现第二个后端的成本从 10–15 天降到 5–8 天 |

**PostgreSQL 的启动触发条件（写死在文档里，避免拍脑袋）**，满足任意一条再排期：

1. 出现 ≥1 个真实的「多中心/多分支各自采集、统一看」的部署需求，且单实例采集覆盖确实不够；
2. 社区有 ≥3 个独立用户明确提出「想接 Grafana/BI 直连数据库」；
3. 有企业用户愿意为「PG 版本」付费或贡献 PR。

在此之前，所有「大规模」问题用**采集侧横向扩展 + 管道去全量重放**解决。

## 3. 「未知节点」的可用性设计

### 3.1 现状评估：`node_key` 够不够？

**`node_key`（`mac:` / `ip:` / `ext:`，`engine.go:37-45`）作为身份机制是够用的**——稳定、跨重启、白名单与资产都能对齐，P0-2 的修复是对的。

但**作为「未知节点」的语义载体，它缺五个维度**：

| 缺失 | 后果 |
|---|---|
| 无**来源**字段（PCAP/抓包/探针/主动探测/人工录入） | 用户对「未知」的信任度无法分层：探针看到的 vs 一次 PCAP 里瞥见的，权重应不同 |
| 无**纳管范围**概念 | 网络域（`domains`）只影响归属与 multi_net，不表达「这些网段是我要看的」 → 无法回答「有没有我没纳管的地方」 |
| 资产只有 `unarchived`/`archived` 二态 | 「这是台打印机，不用管」只能去白名单页操作 → 资产页与白名单页割裂，用户不知道该去哪 |
| 无**人工录入**入口 | 只能靠流量发现。而「账外资产发现」的本质是**与在册台账对照**，没有台账就无法定义「账外」 |
| 无**批量处理** | 几千台账外资产只能一台台点（U4） |

**最大的产品缺口：没有台账导入，就没有真正的「账外资产发现」。** 当前系统只能给出「流量里看到过的东西」的列表，而 README 承诺的核心是「与人工登记的资产台账对照，让账实不符一目了然」（README:23）—— 这个闭环目前是断的。

### 3.2 「随时增加」和「处理」的语义澄清

创始人原话「用户能够随时增加和处理未知节点」，我拆成三层可落地的含义：

| 说法 | 我理解的含义 | 对应功能 | 优先级 |
|---|---|---|---|
| **增加** ① | 手动录入一台已知设备（还没流量） | `POST /api/assets/manual`：IP/MAC/主机名/归属人/位置 → 预置为台账资产 | P1 |
| **增加** ② | 纳管一个新网段 / 部署一个新采集点 | 「纳管范围」管理（CIDR 列表 + 归属探针）+ 探针注册时自动带入 | P1 |
| **增加** ③ | 导入在册台账做对照基准 | CSV 导入 → `ledger` 表 → 三分类统计 | **P1 最高** |
| **处理** ① | 归档（认领入台账） | 已有 `ArchiveAsset`，需支持**批量** | P1 |
| **处理** ② | 忽略/加白（判定为无关，不再提醒） | 新增资产态 `ignored`，等价于对该 node_key 建白名单，但**入口在资产页** | P1 |
| **处理** ③ | 指派责任人 / 加备注 | 已有 `UpdateAsset`，需批量 | P2 |
| **处理** ④ | 导出待处理清单走线下流程 | CSV 导出（仅元数据，合规） | P1 |
| ~~处理 ⑤ 隔离/封禁~~ | — | **永久不做**（合规红线：只打标签、不处置） | ❌ |

### 3.3 功能定义与交互设计建议

**数据模型（最小增量）**

- `Asset.Status` 增加 `ignored`（已忽略）：不计入账外统计、不产生新事件（等价于该 node_key 命中白名单），但**随时可恢复为 unarchived**。
- `Asset` 增加 `source`（`traffic|capture|probe|manual|ledger`）与 `managed_scope`（所属纳管范围名）。
- 新增 `ledger` 表（在册台账）：`asset_no / ip / mac / hostname / owner / department / location / imported_at / import_batch`。
- 新增 `scopes` 表（纳管范围）：`name / cidrs / probe_id / enabled / created_at`。

**交互设计**

1. **资产页默认视图改为「待处理队列」**：`status=unarchived` + 按首次发现时间倒序 + 顶部四个筛选（来源 / 网段 / 是否在线 / 设备类型）。默认不再把已归档的几千台摊在列表里。
2. **多选 + 批量操作条**：勾选后统一「批量归档 / 批量忽略 / 导出」。这是把 U4 从「不可能」变成「3 分钟」的唯一办法。
3. **「台账对照」Tab**：三分类卡 —— ① 账内且在线（相符）② **账外**（发现但台账没有，即真正的账外资产）③ **账内无流量**（台账有但观测不到，可能是关机/下线/被替换/被冒用）。②③ 才是用户真正要的产出，且支持一键导出 CSV。
4. **拓扑图上的未知节点**：未归档节点用虚线描边 + 问号角标；右键菜单直达「归档 / 忽略 / 详情 / 加入白名单」，让用户**在看到问题的地方处理问题**（这是「随时处理」最自然的落点）。
5. **「发现未纳管网段」提示条**：当观测到不属于任何纳管范围的 IP 时，在数据接入页顶部显示「发现未纳管网段 10.20.30.0/24（37 台主机），是否纳管？」一键加入。低成本，直接提升「发现能力」的感知。

## 4. 「发现能力」提升

### 4.1 现状：被动流量为主、nmap 为辅，三个脆弱点

1. **nmap 是外部依赖且默认值激进**：默认 `1-65535` 全端口 + `T4`（`model.go:214-215`），单台几分钟、一个 /24 几小时，结果无节流地逐条 `UpsertPort`（`server.go:1640-1649`）。在没装 nmap 的内网环境里这个能力直接归零。
2. **没有官方探针 agent**：`POST /api/ingest/probe` 只是一个 HTTP 契约（README:119-132），**仓库里没有任何 agent 实现**。要在几十台机器上铺开，用户得自己写一个会抓包、会聚合、会上报的程序 —— 现实中没人会写。**这是「超大规模」落不了地的头号门槛。**
3. **只有端口，没有指纹**：`PortRecord` 只有 port/proto/service（nmap 给的），没有 banner、HTTP title、TLS 证书 CN、设备类型。所以「未知节点」永远只是一个 IP。

### 4.2 缺口清单与价值/成本排序

| # | 能力 | 价值 | 成本 | 判断 |
|---|---|---|---|---|
| **F1** | **官方轻量探针 agent**（Go 单文件，抓包→聚合→按 flows 上报，带 probe_id/location） | ★★★★★ **决定「能不能看到」，是超大规模的前提** | M（3–5 天） | **必做，且应排在很前面** |
| **F2** | **台账导入与账实对照** | ★★★★★ 直接兑现 README 的核心承诺 | M（3–5 天） | **必做** |
| **F3** | **设备类型 / 厂商识别**（MAC OUI 离线小库 + TTL + 端口组合启发式） | ★★★★☆ 账外资产主力就是摄像头/打印机/IoT，识别出「这是海康摄像头」是质变 | S–M（1–2 天） | **高性价比，强烈建议** |
| **F4** | **未纳管网段发现 + 一键纳管** | ★★★★☆ 直接回答「有没有我没看到的地方」 | S（1 天） | **高性价比** |
| **F5** | **资产变更日变化摘要**（新增 / 消失 / 换 IP / 换 MAC / 新开端口） | ★★★★☆ 让「每天看一眼」成为可能 | M（2 天） | 建议 |
| **F6** | **服务指纹**（明文 HTTP 的 Server/Title、TLS 证书 CN、常见明文协议 banner） | ★★★☆☆ 让未知节点变成「未知 Web 服务」 | M（2–3 天） | 可选；注意**只取明文、不解密、不主动交互** |
| **F7** | **探针覆盖度可视化**（每个纳管范围有多少主机、被哪个探针看到、盲区在哪） | ★★★☆☆ 让「覆盖不足」这件事可见 | S（1 天） | 建议，与 F1 配套 |
| **F8** | 主动扫描改造（默认改 Top1000 端口 + 并发上限 + 任务队列 + 结果批量入库） | ★★☆☆☆ 稳定性改进 | S（1 天） | 建议顺手做 |
| ~~F9~~ | 探针自动编排 / 自动下发扫描策略 | — | — | **永久不做**（合规红线 §2.3 of PM-DATA-INGEST-V2：主动发包不得自动化） |
| ~~F10~~ | ML 异常检测 / 行为基线 | — | — | **不做**：单人维护不起，且违反「只打标签」的可解释性要求 |

**结论：把「发现能力」的预算投在 F1 + F2 + F3 上，而不是中心端性能。** 因为在超大规模内网里，用户拿不到全网镜像 → 覆盖靠探针（F1）；覆盖到了以后，价值靠台账对照（F2）和设备识别（F3）兑现。中心端再快，看不到也白搭。

## 5. 分阶段升级路线（P0 / P1 / P2）

**工作量口径**：「天」= **业余天**（约 2–3 有效工时，工作日晚上或周末）。折算成全职 8 小时人日约 ÷3。
对照前两份文档的 S/M/L：本文 S=1–2 天、M=3–5 天、L=6–10 天（业余口径）。

### 5.1 P0 —— 目标：**让系统能在 5 千–1 万台设备的网络里 7×24 跑起来**

核心原则：**只改管道与限额，不改部署形态，不动数据库。**

| # | 解决什么 | 具体做什么 | 验收标准（可测） | 工作量 | 风险与取舍 |
|---|---|---|---|---|---|
| **P0-A** | 瓶颈① 全量重放 | `Aggregator` 增加脏集与 `DrainDirty()`（只返回自上次以来新增/变化的会话）；`main.go:143-157` 的 2s 轮次改消费增量；`Finalize()` 仅保留给 PCAP 一次性导入与 `SessionsFunc`。`ingestProbe`/`ingestPCAP` 的 `syncTopology` 同样改增量 | 构造 10 万会话稳态：① 2s 轮次 pprof CPU 占用从 >60% 降到 **<5%**；② 单探针上报 P95 耗时 **<50ms**（与累计会话数无关）；③ 30 个探针并发上报 10 分钟无 5xx、无内存增长 | **M（4–5 天）** | 风险：增量与「会话累计更新」语义冲突（bytes 是累计值）。取舍：增量只传「有新报文的会话」，Engine 侧幂等累计已支持（`engine.go:396-408`）。必须先补并发单测 |
| **P0-B** | 瓶颈② 内存无淘汰 | Aggregator 加 TTL（`session_idle_ttl` 默认 300s；`closed` 会话 60s 淘汰）；`packetGaps`/`packetLens` 只保留最近 32 个采样（`parser.go:380-382`）；`Engine.sessions` 同步淘汰；`server.savedSessions` 改为按库内存在判断或 LRU | 注入 50 万合成会话持续跑 24h：**RSS 稳定在 <500MB 且不单调增长**；心跳判定（`detect_test.go` 相关用例）无回归 | **S–M（2–3 天）** | 风险：TTL 太短会打断长连接判定（`IsLongConn`）。取舍：长连接会话单独保活，不受 idle TTL 影响 |
| **P0-C** | §1.4 资产静默缺失 | `syncAssets` 改遍历引擎**全量内网节点**（新增 `Engine.AllNodes()`，带 NodeKey 且非 `ext:`），不再用 `Snapshot().Nodes` | 构造 5 个各 60 台的 /24（共 300 台）：资产库 **300 台全部可见**，账外统计 = 300；聚合与下钻行为无回归 | **S（1 天）** | **必须与 P0-D 同时上线**，否则 `/api/assets` 会因节点数暴涨而超时 |

| **P0-E** | 瓶颈⑥ 前端渲染 + U3 列表 | ① `/api/topology` 加 `?limit=`（默认 500 节点，按风险/活跃度优先裁剪）与 `Stats.TotalNodes`，前端显示「共 N 台，已显示前 500 台，请下钻或筛选」；② `topo.js` 加硬上限：>2000 节点强制聚合视图模式（只画子网/位置聚合节点）；③ `/api/assets`、`/api/events` 服务端分页（`limit/offset` + `total`），前端分页器 | 5 万节点的库：① 拓扑页首屏 **<3s** 且缩放/拖拽帧率 **>30fps**；② 1 万条资产列表翻页 **<500ms**；③ 事件列表 1 万条不再一次性返回 | **M（4–5 天）** | 取舍：加上限会损失「全局一览」。用「聚合视图 + 下钻 + 筛选」补偿，不引入 WebGL（单人维护不起） |

| **P0-G** | §1.3 O(M×E) 清理冻结 | `removeNodeLocked` 改为先建「节点 → 关联边」邻接索引，删除只遍历该节点的边；清理任务改为批量收集 keys 后一次性删 | 5 万边 + 1000 台待清理：清理耗时 **<1s**（当前推算数十秒–数分钟），期间 ingest 无冻结 | **S（1–2 天）** | 低风险 |

**P0 合计：约 15–19 业余天**（约 1.5–2 个月业余时间）。
**P0 完成后可用规模（推算）：从 ~1 千台提升到 ~1 万台，且部署形态零变化。**

| # | 事项 | 触发条件 | 工作量 |

| P2-1 | `store` 层接口化（**买期权，可随时做**） | 无（0.5 天，建议下一个空闲窗口就做） | **0.5 天** |
| P2-2 | PostgreSQL / 多实例汇聚 | 满足 §2.4 三条触发条件之一 | **L（10–15 天起）** |

## 6. 关键结论

### 6.1 最该做的三件事

1. **先修管道，别换数据库。** 把「每 2 秒全量重放所有会话」改成增量 + 加会话淘汰（P0-A/P0-B，约 7 天业余时间）。这一项把可用规模从 ~1 千台抬到 ~1 万台，**且不改变部署形态、不增加任何用户可见复杂度**。同时顺手修掉 §1.4 的资产静默缺失（P0-C），否则「账外资产发现」这个核心卖点在任何超过 20 台/网段的网络里都是假的。

2. **把「发现能力」的预算花在采集覆盖与运营闭环上，而不是中心端吞吐。** 发布官方轻量探针 agent（P1-3，决定能不能「看到」）+ 台账导入对照（P1-1，决定「账实不符」能不能回答）+ 账外资产批量处理（P1-2，决定几千台能不能运营完）。超大规模内网的真实约束是「看不到」和「看不完」，不是「写不进」。

3. **给所有列表和拓扑图设服务端上限与前端 LOD**（P0-E）。1 万节点时「功能存在但人用不了」等于没做。用户不会说「你功能不全」，只会说「这东西卡得没法用」然后卸载。

### 6.2 明确不该做的事（会拖垮单人维护）

| ❌ 不要做 | 为什么 |
|---|---|
| **现在换 PostgreSQL** | 解决不了先崩的四个环节（§1.5）；毁掉「零依赖单二进制一键部署」的唯一卖点；单人维护两套 schema/迁移/部署文档是永久负债 |
| **双存储（SQLite + PG 可选）** | 同上，且「可选后端」会吸引用户踩你不常测的那条路径。**只做接口化买期权，不实现第二个实现** |
| **引入 Kafka / ClickHouse / Elasticsearch / 时序库** | 直接违反「内网离线、零依赖、单二进制」定位；运维复杂度与单人维护能力完全不匹配 |
| **微服务拆分 / gRPC / 消息队列** | 单进程是优势不是缺陷。要横向扩展走「多实例采集 + 中心汇聚」，不是把单进程拆开 |
| **把 Detector 并行化** | P0-1 刚用整轮串行化堵住 `fatal error: concurrent map writes`（`detector.go:43-47`）。在 P0-A 把工作量从 O(N) 降到 O(Δ) 之前，并行化收益极小、风险极高 |
| **前端重写为 React/Vue/WebGL** | 现有自绘 SVG 引擎 974 行已投入且符合「零构建、零 CDN」约束。用「上限 + 聚合视图 + 分页 + LOD」解决，不重写 |
| **现在做多租户 / RBAC** | 合规红线（不建权限体系）+ 维护成本；已有可选 OIDC 门卫够用 |
| **未知节点自动隔离 / 告警外发** | 合规红线：只打标签、不定性、不处置、不外发 |
| **为压测数字好看而提前加缓存层** | 先量后改。P1-8 实测之前加缓存，只会掩盖真实瓶颈 |
| **在没有官方 agent 之前谈「探针横向扩展」** | 契约不等于能力。用户不会自己写 agent，没有 agent 的探针方案等于零 |

### 6.3 给创始人的一句话

> **StarMap 现在的瓶颈不是「数据库不够强」，是「每 2 秒把全部历史重做一遍」和「超过 20 台/网段就看不见设备」。这两条加起来约 8 天业余时间就能修完，而换成 PostgreSQL 要 10–15 天，修完还是一样卡。先把管道和可见性修对，再谈数据库。**
