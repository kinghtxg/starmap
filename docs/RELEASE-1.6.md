# StarMap 1.6.0 发布说明

> 主题：**静态清单只能看一次。**
> 发布日期：2026-11-01 · 上一个正式版：1.5.1

---

## 一、这一版在解决什么

1.5 及之前，StarMap 回答的是「现在网里长什么样」——拓扑、资产、端口、风险。
这个问题看一次就过期了。第二天再打开，没有任何地方告诉你：

- 哪台机器是昨天新来的？
- 上周还在的 3389，今天怎么没了？
- 周三起的那轮全网段扫描，跑完了吗？扫出多少？

第三个问题在 1.5 及之前**根本无法回答**：发现任务只存在内存里（最多 50 条），
进程一重启就归零，答案只剩日志里几行 Info。

1.6.0 补的就是这个时间维度，同时把「长期在线跑」必然要面对的三张表的回收路径补齐
（原计划单独发的 1.5.2 并入本版）。

## 二、能力变化

### 1. 主动发现任务账（新页面：发现任务）

| 之前 | 现在 |
|---|---|
| 任务状态只在内存，重启即丢 | 落库 `discover_tasks`，重启后仍可回溯 |
| 最多看 50 条 | 保留最近 500 条，可按状态筛选、分页 |
| 无法停止 | `POST /api/tasks/{id}/cancel`，**真的打断扫描 goroutine** |
| 重启后挂着一堆「运行中」 | 启动时自动收尾为「进程重启，任务中断」 |

任务与结果的分工是刻意的：**只记任务账，不记扫描结果**。端口和指纹已经在
`ports` 表里，两处都存就得处理「不一致时谁对」，而这种不一致从来不会自己消失。

取消有三种结果，分别对应不同处置：

- `404` 任务不存在
- `409` 任务已结束（带上当前状态，不是假装成功）
- `202` 已请求停止，当前主机收尾后退出

「请求停止」而不是「立即杀掉」：一次 TCP 探测可能已经在路上，强行中断会留下一堆半开连接。

### 2. 变更视图（新页面：变更）

不引入快照表，完全由 `ports` 表已有的 `first_seen` / `last_seen` 推导：

- **新增端口**：窗口内首次被发现
- **不再活动**：窗口内没再观测到（且不是窗口内新出现的）

两个词都带了「去重主机数」。300 个新端口来自 2 台机器（一台新上线的业务系统）
和来自 300 台（全网在推一个新客户端），处置方式完全不同——只给端口数会误导优先级。

窗口支持 1 / 7 / 30 / 90 天，页面上方是三张新增趋势小图（资产 / 端口 / 事件）。

### 3. CSV 导出（资产 / 端口 / 事件 / 任务）

结构梳理完的下一步永远是**交给别人**：交给等保整改、交给资产系统对账、交给领导看。
没有导出，用户只能截图或自己写脚本调 API，产品就停在「自己看看」的层级。

两个必须做对的地方：

**防 CSV 公式注入。** 资产名、备注、页面标题都是外部可控内容——页面标题直接来自
被扫描主机返回的 `<title>`。也就是说，**被扫描的那台机器决定了导出文件里的内容**。
扫到一台返回 `=cmd|'/c calc'!A0` 标题的设备，分析师一打开表格就执行了。
以 `= + - @` 开头的非数值单元格一律加前导单引号；纯数字与负数保持原样
（加了引号会让下游脚本 `sum()` 算错）。

**UTF-8 BOM。** 没有 BOM 的中文 CSV 在 Windows Excel 里按 GBK 解码，整列乱码。
而「用 Excel 打开」是这类文件唯一的使用方式。

**规模与并发。** 每页 2000 行流式翻页写，单次上限 20 万行（达到上限补一行说明，
静默截断会让用户以为拿到的是全量）。导出本身不占锁，所以另外加了 2 个并发名额：
名额满时回 429 而不是排队——排队会让浏览器一直转圈，用户以为服务挂了，再点几次
反而把并发推得更高。

**下载失败不该把人踢走。** 前端原来用 `location.href` 直接指向导出地址，
服务端一旦回 401/403（会话过期、只读账号），浏览器会把**整页**跳到一个
白底黑字的 `{"error":"..."}` 上，用户回不到原来的列表页。
改成 fetch 先看状态码，失败时原地弹提示、页面不动；成功再从 blob 存盘。
导出行数在服务端有硬上限，内存边界是确定的。

## 三、修复

### 被取消的任务谎报「全部完成」

`runDiscover` 收尾写的是 `task.Total, task.Done = res.Total, res.Total`。

正常跑完两者相等，看不出问题。一旦被取消或超时中断，界面上出现
「**254/254 已完成**」，而实际一台都没扫完。

这不是一个无关紧要的计数。用户看到「已完成」，得出的结论是
「这个网段扫过了、不用重扫」——**结论直接错**。

修复后 `probe.DiscoverResult` 把「计划扫多少」和「实际处理多少」分开：

```
修复前：status=cancelled total=254 done=254
修复后：status=cancelled total=254 done=4
```

顺带修正状态判定顺序：`context.DeadlineExceeded` 必须排在通用 `err != nil` 之前，
否则 6 小时上限触发时会把 `context deadline exceeded` 原样甩给用户。

### 变更查询的覆盖索引（395ms → 40ms）

「消失」条件是 `last_seen < ? AND first_seen < ?`。只建 `last_seen` 单列索引时，
SQLite 拿到范围后必须**回表**逐行取 `first_seen` 才能判定——
4.3 万行的 `COUNT(*)` 实测 **395ms**。改成 `(last_seen, first_seen)` 复合索引后 **40ms**。

`MarkStalePorts` 同理改用 `(state, last_seen)`。

> **另一个坑值得单独记一笔**：驱动把 `time.Time` 绑成 **RFC3339**
> （`2026-03-04T15:04:05.12+08:00`，带 T），而 SQLite 的 `date()` 只认
> `YYYY-MM-DD HH:MM:SS`（空格分隔）。所以 `SELECT date(col) ... GROUP BY 1`
> **不报错，静默返回 NULL**——所有行落进同一个 NULL 桶，趋势图变成一条平线、
> 变更页显示 0 条，而接口 200、日志无异常。
> 按天分组一律用 `substr(col,1,10)`，见 `internal/store/timefmt_test.go`。

## 四、容量与长期在线（原 1.5.2 并入）

被动分析产品「只进不出」是结构性缺陷。开发机上看不出来，真实网络里几小时就撑爆。

| 表 | 之前 | 现在 |
|---|---|---|
| `sessions` | 无任何回收路径 | `session_retention_days`（默认 30 天） |
| `sessions` | 重启后同一会话重复插行 | 五元组唯一键 + 幂等 upsert |
| `ports` | 三年前的 3389 和今天的 3389 长得一样 | 30 天未观测标 `stale`（不删行） |
| `assets` | 逐节点 SELECT+UPSERT（2000 台=4000 条语句） | 单事务批处理 |
| 检测 | 探针上报同步跑全量检测（3000 会话 42 秒） | `Kick()` 异步触发，2 秒合并 |
| 事件去重 | 每个候选查两次库（O(N²)） | 一轮只建一次索引 |

现场数据支撑这些数字：一台机器跑 3 天，`sessions` 表 60 万行 / 148MB，
按此线性外推一年约 18GB——而界面上看不到任何迹象。

## 六、升级注意事项

1. **无需手工迁移**。`discover_tasks` 表、`sessions` 唯一键、新增索引都在启动时自动创建。
2. **首次启动可能较慢**：`sessions` 补唯一键要先删历史重复行。若表很大（几十万行），
   这一步会花几秒到几十秒，属正常。
3. **`session_retention_days` 默认 30 天**。想保留更久的历史，在 `config.yaml` 或
   系统配置里调大；设 0 表示不清理（不建议，见上表的增长数据）。
4. **任务账从本版开始积累**。1.5 及之前的历史任务不会补录——它们从未落库。

## 七、已知短板（未解决，不粉饰）

- **任务进度不落库**：进程崩溃后重启，任务的 `done` 停在最后一次落库的值（即开始时的 0）。
  可用，但不精确——正在跑的长任务要接受「重启后进度清零」。
- **`MarkStalePorts` 是整批 UPDATE**：2.4 万行约 370ms，跑在维护循环里。
  量级再上一个数量级（20 万行）时应改成分批。
- **导出没有异步化**：20 万行 CSV 在一个请求里写完，大表导出会占住一个连接。
  目前靠「单次上限 + 流式分页 + 并发名额 2」控制，没有后台任务化。
- **变更视图只看端口**：资产的新增/消失、风险事件的状态流转没有进变更页。
  端口是最能反映"网里多了一套系统"的信号，先做这个。
