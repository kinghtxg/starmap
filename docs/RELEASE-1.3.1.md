# StarMap 1.3.1 发布说明

**发布日期**：2026-10-27
**主题**：把 1.3.0 留下的"护栏式妥协"换成真答案

---

## 一句话

1.3.0 为了控制风险，把列表分页做成了"服务端截断 + 前端本地翻页"。这个妥协有个不体面的后果：
**用户在上限之外搜不到的数据，界面上看起来是"不存在"**。1.3.1 把它改成真分页，
并清掉审计中发现的几个同类问题——都属于"不报错，但让人放心地得出错误结论"那一类。

---

## 为什么这个版本值得单独发

如果只看 changelog，这版像是一堆小修补。但它们有一个共同点：

| 问题 | 表现 | 为什么危险 |
|---|---|---|
| 列表本地筛选 + 服务端上限 | 搜不到上限之外的设备 | 用户看到"没有匹配"，于是确信那台机器不存在 |
| `event_retention_days` 重启不恢复 | 改完正常，重启变回默认 | 只在重启时暴露，开发期几乎撞不到 |
| 配置无锁读写 | 偶发读到"改了一半"的配置 | 两个管理员同时操作才会触发，最难以复现的方式报障 |
| 搜索无结果时总数不归零 | 列表空了，徽标还挂着 120 台 | 比不显示更误导 |
| `/api/stats` 全表扫描 | 事件越多首页越慢 | 开销随运行时间线性上升，上线三个月后才开始疼 |

这些都不是"崩溃"，是**产品安静地给出错误答案**。1.3.0 的自查是按"攻击面 + 容量"两个维度做的，
这一版补的是第三个维度：**结论的正确性**。

## 改动明细

### 1. 真·服务端分页 + 服务端搜索

**后端**

```http
GET /api/events?status=pending&type=frp&q=穿透&limit=20&offset=40
GET /api/assets?status=archived&q=负责人3&limit=50&offset=0
GET /api/ports?node_key=mac:aa:bb&q=nginx&limit=100&offset=200
```

响应头：

| 头 | 含义 |
|---|---|
| `X-Total-Count` | **当前筛选条件下**的服务端总数 |
| `X-Result-Limit` | 本次生效的单页条数（夹取后的真实值） |
| `Access-Control-Expose-Headers` | 跨域部署时让 JS 能读到上面两个 |

筛选条件下沉到 SQL，列表与计数共用同一份 `EventFilter`/`AssetFilter`/`PortFilter`：

```go
// 唯一构造点：列表与计数必须共用，否则"共 N 条"迟早和列表对不上
func eventWhere(f EventFilter) (string, []any)
```

搜索覆盖的列：

| 表 | 模糊匹配列 |
|---|---|
| events | `title` `detail` |
| assets | `ips`（JSON 数组文本，能匹配到里面的 IP）`mac` `hostname` `os` `owner` `department` |
| ports | `ip` `service` `product` `version` `title` `banner` `tls_cn` |

**三个容易漏的细节**

1. **LIKE 通配符必须转义**。不转义时用户在搜索框输入 `%` 会命中全部记录，
   输入 `10_0_0_1` 每个 `_` 变成单字符通配。这类 bug 不报错，只让人怀疑"搜索是不是坏的"。
2. **关键字按 rune 截断到 64 字符**。`LIKE '%...%'` 走不了索引，长模式串是免费的 CPU 放大点；
   按字节切中文会切出半个字符。
3. **排序键必须唯一**。端口表补 `id` 兜底、资产表补 `node_key`：
   排序键不唯一时，同一行可能在两页都出现、或两页都不出现——SELECT 的返回顺序不保证稳定。

**前端**

| 页面 | 页大小 | 说明 |
|---|---|---|
| 事件 | 20 | 默认筛「待处置」（运维只关心待办） |
| 资产 | 50 | 状态筛选 + 关键字 |
| 端口 | 100 | 关键字可搜 IP / 服务 / 产品 / 标题 / 证书 CN |

- 筛选变化**必须回到第 1 页**：留在第 5 页会让用户看到"只有 3 条"的假象。
- 输入防抖 300ms：后端是单连接 SQLite，每按一个键发一次请求会堆成队列，越打字越卡。
- **请求序号丢弃过期响应**：快速输入时先发的请求可能后到，会把界面刷成旧结果
  （前端版的数据竞争）。
- 删光最后一页后自动回退一页，不留空表。

### 2. 配置一致性：从"注释约定"变成"可执行断言"

`mergeRuntimeConfig` 的注释里早就写着：

> 约定：**凡是通过 PUT /api/config 能被改的字段，这里都必须恢复**。

然后 `event_retention_days` 就没恢复。注释拦不住人，所以改成三道机器校验：

```
putConfig 实际解析的键  ──┐
                          ├─→ 三向交叉校验，任一缺失即测试失败
mergeRuntimeConfig 恢复  ──┤
                          │
SystemConfig 真实字段   ──┘
```

`cmd/starmap/config_consistency_test.go`：

- `TestPutConfigKeysRegistered`：新增键没登记映射表 → 失败（提醒你去补恢复逻辑）
- `TestEveryWritableKeyIsRestored`：登记了但没恢复 → 失败，并直接打印是哪一项
- `TestConfigKeyFieldsExist`：映射指向不存在的字段 → 失败（防改字段名后守卫静默失效）
- `TestNoDirectCfgFieldAccess`：出现 `s.d.Cfg.字段` 这种绕过锁的写法 → 失败

> 负向验证过：删掉 `EventRetentionDays` 的恢复分支，测试立刻红并指出
> `event_retention_days→EventRetentionDays`。

### 3. 配置读写并发安全

`internal/config.Box`：

```go
box.Get()                              // 返回深拷贝副本
box.Update(func(*model.SystemConfig) error)  // 写锁内改副本，返回 error 则整体回滚
```

`Update` 的回滚语义正是 `PUT /api/config` 需要的：改了 30 个字段、第 31 个非法时，
不能留下"前 30 个已生效、没落盘、重启又变回去"的状态。

副作用（`SetEnabled` / `SetRate` / `SetLimits` / `SetLevel`）统一挪到"配置已被接受"之后执行——
放在解析过程中会让校验失败的那次请求留下已经改掉的运行时状态。

### 4. 其他修复

- **`maintenanceLoop` 每轮重读配置**：此前拿的是启动时的配置指针，后台改保留期要重启。
- **`/api/stats` 改 `COUNT(*)`**：不再把事件全表读进内存循环数。
- **搜索无结果时总数归零**：`api.js` 改用"响应头是否存在"判断，不再用 `total > 0`
  （后者会把 total=0 的响应整个丢弃，meta 里留着旧值）。

### 5. 第二轮审计：把 CI 的假防线换成真防线

改完上面四项后按要求"重复测试"。CI 九 job 全绿，但顺手去核对那条 staticcheck
步骤究竟检查了什么，结论是——**它一行代码都没检查过**。

```yaml
# 修复前
run: |
  go install honnef.co/go/tools/cmd/staticcheck@2024.1.1 || true
  staticcheck ./... || { echo "warning"; }
```

`staticcheck@2024.1.1` 依赖的 `x/tools` 用「负数常量做数组长度」的写法（`-delta*delta`），
在 Go 1.26 下**编译即失败**。于是链条是：安装失败 → `|| true` 吞掉 → 下一步执行一个
不存在的命令 → `|| { echo warning }` 再吞掉。这个 job 永远是绿的，永远打印同一条
warning，看起来像是有静态检查。

修好之后（`@latest` + 装失败即失败 + 打印版本号），`staticcheck 2026.2.2` 第一次真实
运行就报出 **11 项**。逐条处理：

| 问题 | 处理 |
|---|---|
| `verifyIDToken` 的验签 `switch` 缺 `default` | 加 `default` 返回错误 |
| ES256 公钥由裸坐标 `&ecdsa.PublicKey{X,Y}` 拼装 | 改用 `ecdsa.ParseUncompressedPublicKey` 做曲线校验 |
| `NewRequestID() == NewRequestID()` —— 测不出碰撞的断言 | 改为 1000 次去重 + 长度校验 |
| `RequestIDFrom(nil)` 传 nil context（刻意为之） | `//lint:ignore` 加理由，保留用例 |
| 6 处彻底死代码 | 删除 |

两条值得展开：

**① 缺 `default` 的验签 `switch`。** 当前白名单在更前面就拦掉了非 RS256/ES256 的
`alg`，所以**现状不是漏洞**（`alg:none` 进不来）。但"白名单改了、case 忘了加 =
静默跳过验签"是 JWT 的经典杀法。加一条 `default` 返回错误，把未来的疏忽变成
看得见的失败——成本一行，收益是这类事故永远不可能发生。

**② 裸坐标拼装的 ES256 公钥。** `&ecdsa.PublicKey{X: …, Y: …}` 不做任何校验，
一个**不在 P-256 曲线上的点**也会被当成合法公钥。JWKS 是外部输入：身份服务被攻破、
或 DNS 被劫持指向攻击者的 JWKS，就能投毒。接受伪造的点等于接受伪造的签名。
改用 `ecdsa.ParseUncompressedPublicKey`（Go 1.25+，会验证点在曲线上、非无穷远点），
顺带做了两件正确的事：

- 兼容"裁掉坐标前导零字节"的身份服务（不补零会把**合法**密钥拒掉，这是可用性事故）；
- 超长坐标明确拒绝，而不是被 `big.Int.SetBytes` 静默当成另一个数。

新增两条测试，其中「不在曲线上的点必须被拒」做了**负向验证**：把实现改回裸坐标后，
`TestECPublicKeyOnCurve` 立刻红并打印 `不在曲线上的点必须被拒绝`。

最后把 staticcheck **转为阻断**，并把 `|| true` 逃生阀一并拆掉，本地 `make lint`
也接入同一条检查（缺工具时明确报错而不是静默跳过）：

> 留下 `|| true` 等价于留一句"检查不过也能过"。

## 升级说明

**无破坏性变更**，直接替换二进制即可。两点行为变化：

1. **`GET /api/events|assets|ports` 的默认返回条数**从 2000 变为 2000（不变），
   但前端不再一次性拉全量——用脚本直接调这两个接口的话，行为一致。
2. **事件页摘要文案**从 `高危 N · 中危 M · 待处置 K` 改为
   `本页 高危 N · 中危 M · 待处置 K ｜ 共 T 条`：
   全量分项统计需要一趟全表扫描，为三个数字扫几十万行不划算，所以如实标注"本页"。

## 已知边界（1.3.1 收敛后仍存在）

| 边界 | 说明 | 计划 |
|---|---|---|
| 无 TCP 流重组 | 只见单包 | 不计划（收益低） |
| 不解密 TLS | 只有 SNI / 证书 / JA3 / JA4 | 永不（合规红线） |
| 单机单进程 | 无集群 | 定位使然 |
| 前端无自动化回归进 CI | `make ui` 是发布前闸门，需下载浏览器 | 部分 |
| 无 `-race` 本地验证 | 需 gcc，只能靠 CI 三平台 | 否 |
| CSP 保留 `'unsafe-inline'` | 零构建的代价（页面全内联脚本） | 不计划 |
| 指纹长尾 | 70 条规则覆盖不了长尾产品 | 持续补 |

## 与 1.3.0 的关系

1.3.0 是"准备开源"的版本：逐功能审查、攻击面加固、把实现写清楚。
1.3.1 是它的**收口**——把 1.3.0 里为了控风险而明确标注为"待办"的那几项做完，
并把期间发现的同类问题一起清掉。

两个版本都做了同一件事：**把"看起来正常"和"确实正确"之间的差距找出来**。
