Why StarMap

资产底账，为什么总对不上

安全运营的起点是「知道自己有什么」。但内网资产长期处于「看不清」的状态——台账里的不一定在，网络里的不一定在账上。

PROBLEM / 01

账外设备失管

测试机、旁路设备、离职遗留主机散落在网段里，不在任何台账之上，却可能是攻击者的第一落脚点。看不见，就守不住。

PROBLEM / 02

资产底账靠手工

资产登记依赖 Excel 与人工填报，设备更替、IP 变更后底账迅速失真。账实不符是常态，等保审计时只能临时补课。

PROBLEM / 03

影子 IT 难发现

员工私搭的服务、未登记的开放端口、悄悄接入的旁路，构成安全盲区。传统扫描式测绘有周期、有盲点，难以及时覆盖。

How it works

让流量自己「画」出资产地图

不依赖主动扫描，靠被动流量持续感知。三路数据统一汇入一条流水线，拓扑自动生长，账外设备自然浮现。

被动流量测绘

PCAP 导入、网卡抓包、远端探针上报，三路流量统一汇入聚合器，自动生长节点与链路——同 MAC 合并、/24 聚合、边老化、NAT 修复。

账外资产发现

自动发现的主机登记为「账外资产」，与人工归档的台账对照，账实不符一目了然。未登记主机离线超时自动清理，台账始终保持新鲜。

只打标签，不定性

对可疑行为仅产出特征标签（如「疑似 FRP 隧道特征」），不判定违规、不告警外发、不联动封禁、不解密流量。合规边界清晰，可在授权环境放心部署。

Architecture

单二进制，一条流水线

三路数据统一汇入聚合器 → 拓扑引擎 → 检测 → 复核/审计，SQLite 持久化，前端 embed 内嵌，无任何 CDN/外网依赖。

Capability Matrix

能力矩阵

从流量接入到资产归档，一套完整的内网资产测绘闭环。

能力说明状态
ingest三路数据接入：PCAP/PCAPNG 导入 · 网卡实时抓包 · 远端探针上报✅ 可用
topology拓扑自动测绘：同 MAC 多 IP 合并 · /24 聚合下钻 · 边老化 · NAT 修复✅ 可用
assets主机资产库：账外资产自动登记 · 归档归属信息 · 离线自动清理✅ 可用

review复核闭环：确认 / 误报加白 / 暂缓 · 白名单四维度抑制 · 全量审计✅ 可用
auth可选认证：本地账号或 OIDC 单点登录（默认关闭，不做 RBAC）✅ 可用
Quick Start

一分钟跑起来

构建 & 运行
# 纯 Go 构建，无需 CGO
CGO_ENABLED=0 go build -o starmap ./cmd/starmap
./starmap -config configs/config.yaml
# 打开 http://127.0.0.1:8080
导入数据 & 验证
# 导入 PCAP，驱动拓扑生长
curl -F "file=@testdata/out/frp_tunnel.pcap" \
  http://127.0.0.1:8080/api/ingest/pcap

# 测试与验收
go test ./...
bash scripts/e2e.sh
